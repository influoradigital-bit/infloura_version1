## Notes
- `V20260718160000` backs the admin tier-adjust endpoint. Before it, `creator_profiles` had **no** persisted tier — tier was always derived from `total_followers` at read time (`AdminCreatorService.deriveTier`). The override wins over the derived value when set; `AdminCreatorService.resolveTier` centralizes that precedence.
- FK from a pre-admin-panel table (V6) into `admin_users` (V34) — safe under Flyway's strictly-increasing order, same pattern as V36/V38.
- `V20260718180000` closes the phone gap flagged in the L-9 pass (`Workspace#updateContactEmail`/`WorkspaceMemberDtos.WorkspaceReadResponse` javadocs previously called this out explicitly; those comments are now removed since the gap is closed). `phone` follows the same full-replace, blank-clears-it semantics as `billing_email` (`Workspace#updatePhone`), with a loose format check (allowed chars: `+ ( ) - space`, 7-15 digits) enforced in `WorkspaceService#updateMyWorkspace` — not a DB CHECK, same precedent as `tier_override` above.
- `V20260718190000` (`campaigns.hype_config`): single JSON column, same precedent as `target_audience`/`BrandProfile.niche_tags` — the hype block mixes scalars with a `formatLanes` list and only ever applies to `campaign_type = 'HYPE'` rows, so flat columns would be dead weight on every other row. Persisted/read via `CampaignDtos.HypeConfigDto` + `JsonLists.toJsonObject`/`objectFromJson` — note `liveUntil` is typed `String` (not `Instant`) on that record specifically because `JsonLists`'s `ObjectMapper` has no jackson-datatype-jsr310 module registered (a plain `new ObjectMapper()`, unlike Spring's auto-configured request/response mapper), so a temporal type would fail on the storage round-trip. `CampaignService.create`/`update` only ever write `hype_config` when the campaign's `campaignType == HYPE`; a hype block sent on a non-HYPE request is validated as absent-is-fine and silently ignored (`CampaignValidator.validateHypeConfig`). Also folded in: `campaignType` now defaults to `STANDARD` when unspecified on create (previously stayed `NULL` — see V30's note that this was deferred until "the brand-facing form" sends a type; the Hype form now does, so the human REST path picks up the same STANDARD-default convention `CreateCampaignExecutor#parseCampaignType` already uses on the AI-drafted path). `campaignType` remains immutable after creation (not part of `CampaignPatchRequest`) — `update()` can only revise the `hype` block, and only for a campaign that was already created as HYPE.
- **[G3 fix, no new migration]** `CampaignService.update`'s original `hype`-on-PATCH handling did a full-replace of `hype_config` whenever the PATCH included a `hype` block: `JsonLists.toJsonObject(normalizeHype(req.hype()))` overwrote the stored JSON wholesale, so a caller sub-mitting only the fields it meant to change (e.g. `slotsFilled` after a deliverable approval) silently reset every other sub-field it omitted — `audioTrack`/`currency`/`slotsFilled`/`liveUntil` back to their `normalizeHype` defaults (blank/`"INR"`/`0`/blank), and would have failed `validateHypeConfig`'s 5-required-field check outright for anything less than a full resend of `sourceReelUrl`/`hashtag`/`formatLanes`/`perReelRate`/`slotCap`. Fixed by merging the incoming `hype` DTO field-by-field onto the existing stored config (`CampaignService#mergeHype`) before validating and persisting — chosen over "require a complete object on every hype PATCH" because it mirrors `Campaign.applyPatch`'s own existing convention (null sub-field = leave alone, non-null = overwrite) applied one level down into the JSON blob, rather than the full-replace convention used for the *list* fields (platforms/hashtags/targetAudience), which don't have a coherent "patch one element" semantic the way a named-field record does. Validation (`validator.validateHypeConfig`) now runs against the **merged** result, not the raw patch, so partial patches can never leave a required field missing and an explicit invalid value (on a required *or* optional sub-field) is still rejected 400. Test coverage: `CampaignServiceTest` (full hype PATCH, partial-merge anti-data-loss, malformed-merged-value 400, non-HYPE PATCH silently ignored).
