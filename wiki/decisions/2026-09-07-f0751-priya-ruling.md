# RULING — F-0751 / F-0752: `ai_conversations` tenancy for CREATOR-audience Meera

**Ruled by:** Priya (CTO) · **Date:** 2026-09-07
**Reviewing:** `wiki/decisions/2026-09-07-f0751-creator-conversation-workspace-fk.md` (another engineer's write-up, treated as unverified)
**Verdict:** **Option B, amended** — drop `fk_conv_workspace`, add a `tenant_type` discriminator with no default, and add a same-row CHECK binding a CREATOR row's tenant key to its already-FK'd `started_by`. **Option C is rejected: as written it does not work.**

---

## Q1. Which option, and why that one rather than each of the others

### Chosen: Option B, amended

One migration (timestamp convention, matching the newest file on disk `V20260905190000__abuse_throttle_counters.sql`):

```sql
ALTER TABLE ai_conversations DROP FOREIGN KEY fk_conv_workspace;

ALTER TABLE ai_conversations
  ADD COLUMN tenant_type ENUM('WORKSPACE','CREATOR') NOT NULL DEFAULT 'WORKSPACE'
  COMMENT 'WORKSPACE -> workspace_id is a workspaces.id. CREATOR -> workspace_id is a users.id.';

UPDATE ai_conversations SET tenant_type = 'WORKSPACE';

-- Remove the default so a future INSERT that forgets the column FAILS rather than
-- silently labelling a creator row as a brand row.
ALTER TABLE ai_conversations
  MODIFY COLUMN tenant_type ENUM('WORKSPACE','CREATOR') NOT NULL
  COMMENT 'WORKSPACE -> workspace_id is a workspaces.id. CREATOR -> workspace_id is a users.id.';

ALTER TABLE ai_conversations
  ADD CONSTRAINT ck_conv_creator_tenant_is_starter
  CHECK (tenant_type <> 'CREATOR' OR workspace_id = started_by);
```

Three amendments to the document's Option B, each load-bearing:

**(a) No `DEFAULT` after the backfill.** The document's version keeps `DEFAULT 'WORKSPACE'` permanently. That default is the same failure shape as the one that caused F-0751: an unset field that quietly means something wrong. A creator row inserted by code that forgot the discriminator would be indistinguishable from a brand row in exactly the DPDP export/deletion path V74 exists to serve.

**(b) `ck_conv_creator_tenant_is_starter` — the part the document missed.** Its Option B "Against" says integrity becomes "an application-layer promise." That is only half true, and the half that is false matters. `ai_conversations` already carries a second FK: `CONSTRAINT fk_conv_user FOREIGN KEY (started_by) REFERENCES users(id)` (`V12__ai_conversations_messages.sql:12`). For a creator row, `workspace_id` and `started_by` are written with the *same value*:

- `CreatorMeeraController.java:142-143` — `creatorContext.requireCreatorProfile(principal)`, then `profile.getUserId()`
- `CreatorContextService.java:47-51` — `requireCreatorProfile` resolves via `findByUserId(principal.getUserId())`, so `profile.getUserId()` is `principal.getUserId()` by construction
- `CreatorMeeraController.java:160-162` — both are passed to `startOrResumeForCreator(creatorUserId, principal.getUserId(), ...)`
- `MeeraSessionService.java:197-198` — `.workspaceId(creatorUserId).startedBy(userId)`

So a CREATOR row's tenant key is already transitively FK-anchored to `users(id)`. The CHECK turns that from a coincidence of two call sites into a database rule. Cost: one line. Gain: the creator half of the table keeps referential integrity after `fk_conv_workspace` is gone.

**(c) The column keeps the name `workspace_id`.** Renaming is not free: the same value is the `workspaceId` claim on both minted tokens (`MeeraSessionService.java:393, 397`), the `workspace_id` key on influora-ai's CREATOR context payload, and the argument `MeeraContextService.assembleCreatorContext` resolves through (`MeeraContextService.java:219-226`). The discriminator plus the column COMMENT carry the truth; a rename would touch the cross-service contract for cosmetics.

### Why not Option A

A is B minus the discriminator. It unblocks Meera in one statement, and everything I verified says it is *safe* — but it leaves the table in the exact shape that produces the next incident. `CreatorAgentConversationService.exportConversation` / `deleteConversation` (`CreatorAgentConversationService.java:84-115`) reach `ai_conversations` by primary key after an ownership check against the rollup, so they are fine today. The moment anyone writes a DPDP sweep, an admin export, or a retention purge that starts from `ai_conversations` rather than from `meera_creator_conversations`, there is nothing in the row to tell a creator's personal data from a brand's operational data. The discriminator costs one column while the table holds 4 rows (count **UNVERIFIED** — production data, not queried). It will never be this cheap again. The document itself concedes this ("If A is taken, B should follow quickly"); I am declining to create the debt rather than scheduling its repayment.

### Why not Option C — it is broken, not merely large

The document calls C "the only option where the database enforces the rule" and prices it as "the largest of the three but still small." Both claims fail on inspection. C sets `workspace_id` to NULL for creator rows. Three consequences the document does not mention:

1. **It kills the creator write-back path.** `MeeraInternalController.java:325` resolves the tenant for influora-ai's assistant write-back as `onBehalfAuthResolver.resolveForWorkspace(onBehalfJwt, conversation.getWorkspaceId())`, and `OnBehalfAuthResolver.java:89-92` rejects outright when `bodyWorkspaceId == null`. Under C, every creator conversation returns null there. The ASSISTANT reply is never persisted, `recordTurnForUser` at `MeeraSessionService.java:610-613` never runs, and the DPDP list/export the consent screen promises stays permanently empty. `MeeraInternalController.java:357-360` (`/turns/release`) has the identical shape. C trades a 409 at session start for a silent data-loss failure one step later — strictly worse, because the 409 is visible.

2. **It silently removes a concurrency guard.** `V12__ai_conversations_messages.sql:9` is `UNIQUE KEY uq_conv_active (workspace_id, status)`. Today that key is what makes `startOrResumeForCreator`'s find-then-create (`MeeraSessionService.java:182-189`) safe under a double-click: the loser of the race hits the unique constraint. MySQL permits unlimited NULLs in a unique index, so under C every creator row escapes that key and nothing replaces it — C would need `UNIQUE KEY (creator_id, status)` added, which it does not specify.

3. **Its identifier-unification claim is self-defeating.** C proposes `creator_id` keyed on `creator_profiles.id`. But `MeeraSessionService` never has a `creator_profiles.id` in scope on a creator turn — it holds only the user id, which is why `CreatorAgentConversationService.recordTurnForUser` exists as a translation helper at all (`CreatorAgentConversationService.java:126-140`). Under C the session service would hold the user id (for both token claims and the Python context lookup) *and* need the profile id (for every row lookup). That is three identifiers in the hot path where there are two today. C's stated benefit — "resolves the identifier mismatch" — is the opposite of what it produces.

C is not a bigger version of the right answer. It is a different answer that has not been traced against the code.

### Why not Option D

I agree with the document's rejection and the reasoning behind it: `workspaces.type` is `ENUM('BRAND','AGENCY')` (`V2__core_auth.sql:27`), and admitting a third member means auditing every read of `workspaces` for a missing `type` filter. `CampaignRepository.java:66` and `:81` are two such reads that filter on `w.type = 'BRAND'` today and would survive; the risk is the ones that do not filter. Correctly closed.

### The honest cost of B

`fk_conv_workspace` protected brand rows too, and no polymorphic-column design can keep it — MySQL has no conditional foreign key. After B, a bogus brand `workspace_id` inserts silently where today it is rejected. Residual mitigation, verified: brand conversations are only ever created from a workspace already resolved from the database, and `campaign_intents.workspace_id` (`V13__campaign_intents.sql:20`) and `meera_tool_calls.workspace_id` (`V14__ai_credits_tool_calls.sql:31`) both retain real FKs to `workspaces`, so a bogus brand tenant key is still caught the first time any tool or intent is written. This is a real, accepted loss, not a wash.

## Q2. V74's recorded decision — right then, right now, and am I reversing it

**I am not reversing it. It stands.**

`V74__meera_creator_conversations.sql:3-7` records: a creator-scoped, fast-sortable view for DPDP list/export/delete, built "without adding a nullable creator_id to the shared (BRAND + CREATOR) ai_conversations table."

**Was it right at the time (2026-09-03)?** Yes, on its own terms. The rollup buys two things a nullable column on the shared table would not have: the composite index `(creator_id, last_message_at DESC)` (`V74:22`) that the conversation list actually sorts on, and `ON DELETE CASCADE` from `creator_profiles` (`V74:17-18`), which makes creator deletion clean up the DPDP index automatically. Both are real. The `schema-changes.md` entry for V74 states the same rationale independently.

**But it was mis-scoped, and that is the root cause of F-0751.** V74 decided an *indexing* question and was subsequently treated as having decided a *tenancy* question. It declined to add a creator column; it never authorised overloading `workspace_id` with a `users.id`, and it did not check whether the shared table's existing constraints permitted such a value. `V12__ai_conversations_messages.sql:11` had constrained that column to real workspaces since the brand-only era. Nobody reconciled the two. The defect is not that V74 chose wrongly — it is that a decision about an index was allowed to imply a decision about a foreign key.

**Is it right now?** Yes, and now for a stronger reason than in September. Option C is the only option that would reverse it, and Q1 shows C is non-functional against `MeeraInternalController.java:325` and `OnBehalfAuthResolver.java:89-92`. V74's decision survives on its merits here, not by default: the rollup remains the correct home for the DPDP view, and `ai_conversations` remains a single shared table with a single tenant column.

**The condition under which I will reverse it.** Two triggers, either alone sufficient — bring it back to me, do not decide it in a fixer:
1. A creator conversation can be started by someone who is not that creator (an agency or manager acting on their behalf). That breaks `workspace_id = started_by` and invalidates `ck_conv_creator_tenant_is_starter`.
2. Creators need more than one concurrent conversation *and* DB-enforced tenancy at the same time. `uq_conv_active (workspace_id, status)` cannot express "many conversations, one active" on a polymorphic column.

## Q3. Independent verification of "nothing joins `ai_conversations` to `workspaces`"

**Verdict: the claim is true as stated, and the inference drawn from it is incomplete.** Dropping the FK is safe — but not for the reason the document gives.

What I checked and found:

| Surface | Finding |
|---|---|
| JPA association | `AiConversation.java:20-21` — `workspaceId` is a plain `@Column` `String`. No `@ManyToOne`, no `@JoinColumn`, no association to `Workspace` anywhere in the entity. |
| Repository | `AiConversationRepository.java:9-18` — three derived finders (`findByWorkspaceIdAndStatus`, `findFirstByWorkspaceIdAndStatusOrderByLastMessageAtDesc`, `findByIdAndWorkspaceId`). **No `@Query`, no `nativeQuery`, no JPQL of any kind.** |
| Consumers | Exactly two classes inject `AiConversationRepository`: `MeeraSessionService.java` and `CreatorAgentConversationService.java`. Every call site is a save, a `findById`, or one of the three derived finders. |
| Hand-written JPQL / native SQL across all repositories | The only `JOIN workspaces` in the codebase is `CampaignRepository.java:66` and `:81` (`campaigns` → `workspaces`, `WHERE w.type = 'BRAND'`). Neither touches `ai_conversations`. |
| Admin / export paths | The only export path over conversations is `CreatorAgentConversationService.exportConversation` (`:84-104`), which goes rollup → `findById` → `ai_messages`. `deleteConversation` (`:106-115`) is the same shape. Neither reads `workspaces`. |
| Ops runbook SQL | `influora-api/SERVER-DATABASE-GUIDE.md:355-384` gives single-table CRUD only. The one join in the whole guide involving conversations is `SERVER-DATABASE-GUIDE.md:3010-3014`, `ai_conversations JOIN ai_messages`. No workspace join. |
| Python (influora-ai) | No database access to `ai_conversations` at all. `conversation_id` appears only as a JWT claim and an HTTP payload field (`app/auth/service_token.py:85, 415`; `app/routes/chat.py:361-368`; `app/clients/spring.py:202-218, 347-369`). |
| Inbound FKs on `ai_conversations` | `campaign_intents.conversation_id` (`V13:19`) and `meera_tool_calls.conversation_id` (`V14:32`). Both are children; neither is affected by dropping `fk_conv_workspace`. |

**Where the document's reasoning is incomplete.** Its Option A "For" reads: "nothing joins through the FK, so nothing else breaks." Absence of a SQL join is not absence of a dependency. Two code paths *do* treat a conversation's tenant key as a workspace primary key:

- `MeeraSessionService.java:378-380` — `workspaceRepository.findById(workspaceId).orElseThrow(WORKSPACE_NOT_FOUND)`
- `MeeraContextService.java:166-168` — the same lookup, on the BRAND context path

Those are functional joins written in Java. They are safe only because both sit inside an audience branch — `MeeraSessionService.java:332-334` gates on `userType == UserType.CREATOR`, and `MeeraContextService.java:151-155` routes CREATOR to `assembleCreatorContext`, which resolves `creatorProfileRepository.findByUserId(...)` instead (`MeeraContextService.java:219-226`). So the correct statement is: *dropping the FK is safe because every workspace lookup off a conversation's tenant key is already audience-gated in application code* — not *because nothing joins*. If either branch is ever removed or a new unbranched consumer is added, a creator conversation produces a 404 `WORKSPACE_NOT_FOUND`, and no FK will be there to have prevented it. That is what the discriminator column is for.

**Claims in the document I could not verify** (production read-only reasoning only, per the constraint — no command was run against the server): the 4 / 131 / 31 row counts, the verbatim 409 response text, "MySQL 8.4 (this box)", and "every local build reports `Tests run: 2673 … Skipped: 15`". All **UNVERIFIED**. Note that `AbstractIntegrationTest.java:141` pins the test container to `mysql:8.0.40`, not 8.4 — CHECK constraints are enforced from MySQL 8.0.16 onward, so the amended migration is valid on both, but the ruling does not depend on the 8.4 claim being true.

## Q4. F-0752 — the `users.id` vs `creator_profiles.id` split

**Yes, the chosen option settles it. It settles on `users.id` for `ai_conversations`, and it deliberately leaves `meera_creator_conversations.creator_id` on `creator_profiles.id`.**

`users.id` is not an accident on `ai_conversations`; it is the only value that works. The same value is:

- written to `workspace_id` (`MeeraSessionService.java:197`)
- minted into the stream token's `workspaceId` claim (`MeeraSessionService.java:393`)
- minted into the on-behalf token's `workspaceId` claim (`MeeraSessionService.java:397`)
- asserted equal to the request body by `OnBehalfAuthResolver.java:86-92`
- the key influora-ai's `POST /internal/meera/context` resolves through — `MeeraContextService.java:219-222`, `creatorProfileRepository.findByUserId(creatorUserId)`
- read back off the row to authorise the assistant write-back (`MeeraInternalController.java:325`)

`creator_profiles.id` is likewise not an accident on `meera_creator_conversations`: it is what the FK and `ON DELETE CASCADE` at `V74:17-18` require, and what the `(creator_id, last_message_at DESC)` index at `V74:22` is built on.

So the two tables are each keyed correctly for their own job. F-0752 is **not** a defect to be unified away — it is a translation, and it already has exactly one translation point, `CreatorAgentConversationService.recordTurnForUser` (`:137-140`), whose javadoc states the reason. What *is* a defect is that neither identity was expressed anywhere the database could see, so both were invisible to review and to every test.

**F-0752 is therefore closed as: by design, now declared and constrained.** The `tenant_type` column plus its COMMENT declare which id space `workspace_id` holds; `ck_conv_creator_tenant_is_starter` makes the `users.id` claim enforceable by tying it to the column that already FKs `users(id)`. No data migration on either table. Anyone proposing to unify the two identifiers should read Q1's third objection to Option C first.

## Q5. Merge precondition

**I agree with the document, and it is BLOCKING, not advisory.** But its wording ("must actually execute rather than skip") is not satisfiable as written, so here is the precondition in enforceable form.

Why the document's wording fails: `DockerAvailableCondition.java:37-50` disables any `AbstractIntegrationTest` subclass when the Docker daemon is unreachable, and `AbstractIntegrationTest.java:52-66` records that this sandbox cannot reach it. "Must run on a developer machine" cannot be met here. The place with Docker is CI.

The near-miss makes the case better than the document does. A Testcontainers test for this exact slice already exists — `MeeraCreatorPhaseABootValidationTest` (`influora-api/src/test/java/com/influora/integration/dbconstraints/MeeraCreatorPhaseABootValidationTest.java:52-96`). It boots Flyway against real MySQL and asserts `creator_agent_preferences` and `meera_creator_conversations` exist (`:79`). It never inserts an `ai_conversations` row. A test written *for this feature*, running *against a real schema*, missed F-0751 — because it verified that tables were created, not that the feature's own write succeeds. Existence assertions do not catch constraint contradictions. Only a write does.

### The gate — all five, before merge

1. **A new `AbstractIntegrationTest` subclass** (`MeeraCreatorSessionConstraintIntegrationTest`, alongside the existing `integration/dbconstraints/` classes) that inserts a real `users` row, a real `creator_profiles` row, and then persists an `ai_conversations` row through `MeeraSessionService.startOrResumeForCreator` — the actual production entry point, not a hand-written INSERT — and asserts the row lands with `tenant_type = 'CREATOR'`.
2. **It is observed RUN, not skipped, in CI.** The evidence is the `backend-ci.yml` surefire output for that class showing a non-zero run count with `Skipped: 0` for that class specifically. A green build whose skip count silently absorbed it does not close this gate. (`Skipped: 15` + `BUILD SUCCESS` is precisely how F-0751 reached production.)
3. **Falsification.** The new test must be shown FAILING against the pre-migration schema — i.e. run it once with `fk_conv_workspace` still in place and capture the `DataIntegrityViolationException`. A test that has only ever been green proves that it ran, not that it can catch anything.
4. **Negative coverage for the CHECK.** One assertion that a CREATOR row with `workspace_id != started_by` is rejected. `ck_conv_creator_tenant_is_starter` is a new constraint that the code can violate, which is the same category of thing that caused this incident; it does not merge unproven.
5. **A `wiki/processes/schema-changes.md` row**, per the standing rule at the head of that file. It must state the brand-side FK loss explicitly as an accepted cost, so the next person to read that log is not surprised by a table with a `workspace_id` and no FK on it.

Items 1–4 are blocking. Item 5 is blocking by existing team rule, not by this ruling.

## What this ruling deliberately does NOT fix

Named so nobody reads silence as coverage.

1. **The brand side loses `fk_conv_workspace` permanently.** No polymorphic-column design can keep it (MySQL has no conditional FK). Accepted; residual protection is the FKs on `campaign_intents.workspace_id` (`V13:20`) and `meera_tool_calls.workspace_id` (`V14:31`).
2. **The column is still named `workspace_id` while holding a `users.id` for creator rows.** Rename deferred — the name is part of the influora-api ↔ influora-ai token/payload contract.
3. **`uq_conv_active (workspace_id, status)` (`V12:9`) still means one conversation per tenant, forever.** No code path in `src/main` ever writes `DORMANT`, `CAMPAIGN_CREATED`, or `PAUSED_CREDITS` — I grepped `ConversationStatus.(DORMANT|CAMPAIGN_CREATED|PAUSED_CREDITS)` across all of `src/main` and found **zero** matches; `ConversationStatus.java:3-8` declares all four. So every row is `ACTIVE` for life, and `CreatorAgentConversationService.listConversations` (`:70-81`) returns a list that can never hold more than one entry. That is a product gap, filed separately, not a schema defect. Note it is a guard Option C would have *removed* without noticing.
4. **The identifier split between the two creator tables stays** (Q4). Declared and constrained, not unified.
5. **`deleteConversation` (`CreatorAgentConversationService.java:106-115`) does not clear `campaign_intents` or `meera_tool_calls` children** before deleting the `ai_conversations` row. Unreachable for creators today because both child tables FK `workspace_id` to `workspaces` and a creator turn can never write one. It becomes reachable the day creator tools ship. Out of scope; flagged.
6. **The Testcontainers-skip problem generally.** This gate covers one path. Every other DB constraint in this schema is still unproven on a developer machine, and the 15 skipped classes remain skipped.
