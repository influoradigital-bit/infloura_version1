Findings — all closed onto one gate

Each finding below is stated as it was found on 2026-09-01. All six are now closed against .proof-os/gates/F-0392-F-0397-onboarding-field-persistence.sh, which runs the real suites rather than grepping for the fix — so a differently-spelled reintroduction still turns it red. The gate was falsified before being trusted: run against deliberately reverted source, four of its seven frontend assertions failed on the exact pre-fix symptoms. The one thing not fixed is consent persistence, tracked as F-0398.

HIGHBrand onboarding phone is still discarded
influora-api/.../dto/auth/BrandRegisterRequest.java:9 · src/pages/brand-onboarding.tsx:76

The wizard marks Mobile number Required and validates it, and the page now sends it. No server DTO accepts it, and no service writes it. The in-code comment claims this was fixed; the data loss is unchanged.

Fix · Add a phone component to BrandRegisterRequest, normalize through IndianPhoneUtils in AuthService.brandRegister, and call workspace.updatePhone before save.

HIGHAdmin still cannot see creator phone numbers
influora-api/.../dto/admin/AdminCreatorDtos.java:20

The originating complaint of the ticket. Neither admin creator DTO carries phone, so the panel renders its “not provided” fallback for every creator even after one saves a number in settings. The frontend was written against an assumed contract and says so in its own comment.

Fix · Add phone to CreatorSummaryDto and CreatorDetailDto, populate from User.getPhoneNumber() in the mappers, then drop the FLAG FOR CONFIRMATION notes in admin.types.ts.

HIGHConsent is asserted but never asked for, and never stored
src/pages/brand-onboarding.tsx:73

No terms checkbox is rendered in either live step, the payload hardcodes true, and the server's @AssertTrue therefore can never fail. No column, timestamp, or policy version records the agreement.

Fix · Render a real Terms and Privacy checkbox, gate the submit on it, send the real value, and persist accepted_at plus policy version.

MEDIUMcompanySize writes values the admin API rejects
onboarding-steps.tsx:145 · AdminBrandService.java:775

Onboarding writes twelve display strings; admin accepts only STARTUP, SMB and ENTERPRISE and throws INVALID_BRAND_SIZE otherwise, so an onboarded brand's size can never be re-saved through admin. The unknown value passes through raw into a frontend type declared as that closed union.

Fix · Pick one vocabulary — map at write time, or widen the union and backfill.

MEDIUMLogo lost if the user advances mid-upload
src/components/brand/onboarding/onboarding-steps.tsx:884

Continue is not disabled while the R2 upload is in flight and validate() does not check it, so logoUrl resolves to undefined and the entity writes null — with the preview still on screen and no error shown.

Fix · Pass the disabled prop StepFooter already accepts while isUploadingLogo is true.

MEDIUMEvery automated gate greens on a half-applied feature
influora-api/src/test/java/com/influora/service/CreatorProfileServiceTest.java

Compile, typecheck and 21 backend tests all pass. None asserts that a brand's phone reaches the database, and none covers the admin phone DTO — so CI cannot tell “done” from “frontend done, backend missing”.

Fix · Add the two tests that fail today: brand-register persists phone, and CreatorSummaryDto exposes it.

LOWDead members left in OnboardingData
src/components/brand/onboarding/onboarding-steps.tsx:84

teamMembers, walletAmount, gstin, pan and the four KYC document members have had no readers since the wizard went from six steps to three. Harmless, but the type reads as though the wizard still collects them.

Fix · Delete them; the deferred-collection comment already documents where they moved.
