## Part B — Gaps Between Individual Reviews (the actual point of this capstone)

Each individual task review was correctly scoped to its own task. Stepping back, I checked for interactions no single review's scope would have caught. I ran a dedicated cross-wave call-graph trace (webhook controllers → services → repositories → entities) rather than relying on memory of the individual reviews.

### Gap #1 — REAL, ACTIONABLE: the E2 HIGH-2 accepted-risk condition was never actually satisfied by Wave D1

This is the most important finding of this capstone review, and it would not have surfaced from any single task's review.

- E2's rework sign-off (`wiki/errors/idempotency-fixes-E2-security-review.md:139-142`) explicitly downgraded the `/webhooks/conversion` pre-poisoning HIGH to **ACCEPTED-RISK**, on the **binding condition**: *"the Wave D1 per-brand HMAC signature verification for `/webhooks/conversion` (and `/redemption`) MUST land before this endpoint's data is allowed to feed any creator-facing payout/ranking decision. If D1 slips or is descoped, this residual re-escalates to HIGH."*
- I traced what D1 actually shipped: `ShopifyWebhookSignatureVerifier` HMAC-SHA256 verification was added to `ShopifyWebhookController`'s own **new, separate route** (`POST /webhooks/shopify`), confirmed via `wiki/errors/wave-d1-shopify-integration-QA.md:37,51`. `ConversionWebhookController` — the actual endpoint (`/webhooks/conversion`, `/webhooks/redemption`) the E2 condition names — was never touched by D1's diff. I confirmed this directly: `grep -n "HMAC\|Signature\|signature" influora-api/src/main/java/com/influora/web/ConversionWebhookController.java` returns **zero matches**. The class javadoc still documents it as intentionally unauthenticated by design (pre-Wave-D1 trust model), unchanged.
- D2 (WooCommerce) similarly added HMAC only to its own `/webhooks/woocommerce` route.
- **Net effect:** the condition that was supposed to close (or keep closed) E2's HIGH-2 residual was never met. Per the review's own words, this "re-escalates to HIGH."
- **Why this didn't surface in any individual task review:** D1/D2's reviews were scoped to their own new endpoints and correctly found those endpoints sound. E2's review correctly named its condition and routed it ("Arjun keep Wave D1 HMAC bound to this endpoint as the accepted-risk condition" — `SHARED_CONTEXT.md:211`). Nobody closed the loop to confirm the named condition was actually satisfied once D1 shipped — a classic gap-between-reviews: the condition-setter assumed a future task would satisfy it; the future task solved a related-but-different problem and nobody diffed the two.
- **Current exploitability:** `/webhooks/conversion` and `/webhooks/redemption` remain public, unauthenticated, and unsigned. For fixed/known-price orders, an attacker who knows the UTM ULID (public, embedded in a posted tracking link) and the exact order amount can pre-poison the derived idempotency key and suppress a brand's real conversion — attribution/revenue-suppression, not double-payout. Rate-limiting (shared `"tracking"` bucket, itself weakened by the separately-tracked per-IP-only issue, Gap noted below) is the only remaining mitigation.
- **My verdict:** this is a **genuine open HIGH**, not a LOW/MEDIUM residual as currently reflected anywhere in the tracker. It is not new code risk introduced this session, but the aggregate view changes my risk assessment — it should be tracked as an explicit, named launch-blocker-adjacent item, not left implicit inside a closed-out E2 doc.
- **Recommended fix (not yet built, flagging for Vikram/Arjun):** add HMAC or shared-secret signing to `ConversionWebhookController`'s two routes, following the exact precedent D1/D2 already established for their own webhook controllers. This is a well-understood, bounded fix — not new architecture.

### Gap #2 — REAL, lower severity: affiliate commission math trusts webhook order-amount with no upper bound

Also not caught by any individual review, because D1/D2/D4's reviews were scoped to workspace-isolation and idempotency-correctness, not payload-value trust.

- `AffiliateEarningsService.validateAndCompute`: `commissionAmount = redemption.getOrderAmount().multiply(DEFAULT_COMMISSION_RATE)` — a fixed flat 10%, so coupon-configuration edge cases (percentage vs. fixed discount, code reuse, workspace mismatch) do NOT corrupt the rate; those are separately and correctly blocked by `UNIQUE(redemption_id)`+idempotency and by `RedemptionService.validateCode`'s workspace-scoped lookup (the D1 fix).
- However, `orderAmount` itself flows unbounded from the webhook payload (`ShopifyOrderWebhookPayload.totalPrice()` / `WooCommerceOrderWebhookPayload.total()`) straight into commission math. `RedemptionService.doRedeem`'s only guard is `orderAmount.signum() < 0` (non-negative) — no upper bound, no cross-check against any real payment/gateway record.
- Since the webhook body content is controlled by whoever owns the *connected store* (a legitimately-OAuth'd brand, or anyone who can manipulate an order in that store before the webhook fires), a brand's own store can report an inflated `total_price` paired with a valid discount code and drive `commissionAmount` arbitrarily high with no sanity bound.
- **Blast radius:** this is closer to self-inflicted (a brand manipulating its own store data primarily costs the brand, since AffiliateEarning is workspace-scoped and settlement is a ledger-only no-RazorpayX-disbursement mechanism per the D4 production gate) than a cross-tenant issue — no cross-workspace leak, no double-payout. But it is a genuine financial-integrity gap that was in scope for neither D1, D2, nor D4's individual reviews (all three explicitly focused on tenant isolation and double-spend/idempotency, not amount-plausibility).
- **My verdict:** MEDIUM, non-blocking for this build's launch (the ledger-only/no-disbursement gate means no real money moves yet regardless), but should be logged as a tracked backend item before RazorpayX disbursement is ever wired to `AffiliateEarning.SETTLED` — otherwise this becomes a real-money exposure the day disbursement ships.

### Gap #3 — checked, NOT a gap: Wave D webhook/redemption paths cannot reach BrandSafety (Wave C)

Dedicated call-graph trace confirms full structural separation:
- `ShopifyWebhookController.receive` / `WooCommerceWebhookController.receive` both terminate in `RedemptionService.redeem` → `doRedeem`, which writes only `CouponRedemption`/`CouponCode`/calls `AffiliateEarningsService`/`AuditLogService`. Neither touches `CreatorScore` or any BrandSafety class.
- The only writer of `CreatorScore.brandSafetyScore`/`garmFlagsJson` is `ScoreCalculationJob`, a pure `@Scheduled` cron job with no caller from any controller/webhook.
- The only writer of `MediaMetric.caption` (the field BrandSafety's prompt construction consumes) is `MetricsPollingJob` (Instagram polling) — confirmed no other writer exists.
- No webhook-derived field (order data, discount code, customer info) has any path into `ContentItem` or the `/internal/brand-safety` request body.
- **Verdict: genuinely isolated, no gap.** This is the one cross-wave question I checked that came back clean.

### Gap #4 check — rate-limit per-IP-only limitation (`task_568d968e`)

- Confirmed status: tracked as non-blocking LOW-to-MEDIUM across D1/D2/D3 consistently, root cause (`AuthRateLimitFilter.bucketFor`'s `clientIp(request) + "|" + bucket` keying, plus unconditional trust of `X-Forwarded-For` with no verified trusted-proxy hop-count config) is unchanged by any wave, correctly not fixed piecemeal.
- **My aggregate view does NOT escalate this.** It is availability-only (budget exhaustion, not data exposure or mutation), and — importantly, per Gap #1 above — the endpoint this rate-limit is the *sole remaining mitigation for* (`/webhooks/conversion`) has a more direct, more severe (attribution-suppression) issue that should be fixed on its own merits regardless of the rate-limit question. Fixing Gap #1 reduces reliance on this rate-limit as a backstop for that specific endpoint. Still recommend the cross-cutting `AuthRateLimitFilter` fix (per-shop/workspace scoping, or trusted-proxy hop count) as tracked, non-blocking.

### Gap #5 check — D5 backend follow-ups (integration status/disconnect endpoint, affiliate earnings read endpoint)

- Read `wiki/errors/wave-d5-backend-follow-ups.md` in full. Both are **read-only or delete-only** endpoints (GET status, POST disconnect, GET earnings) — none of the three introduce a new mutation/money path. Disconnect only removes a stored token/integration row (no cascading side effects to redemption/settlement logic, which key off `workspace_id` on their own tables, not integration-row existence).
- **Verdict: genuinely non-blocking for this build's launch, confirmed.** These are UX-completeness gaps (frontend shows honest "not available yet" amber alerts, no fabricated data), not security gaps. No change to my risk assessment.

### Gap #6 check — E-JWKS (Spring→Python auth, staging-only)

- Re-read the ADR (`wiki/decisions/2026-07-07-spring-python-service-auth-jwks-gap.md`) in full for this capstone. This is an availability/rollout gap, not an integrity vulnerability, and it is explicitly named as a hard **E7 launch-approval blocker** (not an E4/red-team blocker) in the ADR itself — Swapnil's gate, correctly sequenced after E4.
- **Verdict: correctly classified, correctly gated at E7 not E4. No change to my risk assessment.** I reconfirm the binding condition stands: any future relaxation of `ALLOWED_ALGS` or shared-HS256 shortcut requires my and Priya's explicit re-approval — flagging this explicitly in this sign-off so it survives session boundaries.

### Gap #7 check — `result_digest` semantic-naming note from E2

- This was a naming/clarity observation, not a security finding, in the E2 rework trace (`markCompleted(String resultDigest)` is used to store literal message-ID references for `sendTurn`, not a true content digest/hash, for other callers). Re-checked: no security implication — the field is opaque bookkeeping metadata consumed only by the same service that wrote it (`findResultRef`), never parsed/trusted as a hash by any other code path. **Confirmed non-blocking, cosmetic only.**

## Part E — Overall Launch-Readiness Verdict (Security)

## SIGN OFF WITH CONDITIONS

The security posture across this entire build is strong: every genuine CRITICAL/HIGH finding raised during individual task reviews traces to a closed, adversarially re-confirmed fix (Part A). The review pipeline caught real, non-cosmetic bugs at every layer — cross-workspace fund misdirection (ContractService), silent commission loss (D4 self-invocation), replay-correctness (sendTurn), and multi-round prompt-injection hardening (C2) — and none of them shipped un-fixed. Cross-wave structural isolation between Wave D (commerce webhooks) and Wave C (BrandSafety) is genuinely clean, not just assumed. Pre-session Phase 1-3 sign-offs hold under this session's changes.

However, this capstone review surfaced one **finding that changes the aggregate risk picture and must be treated as a condition of sign-off**, not merely a footnote:

**Condition 1 (must fix before this can be called a clean sign-off):** `ConversionWebhookController`'s `/webhooks/conversion` and `/webhooks/redemption` endpoints remain unauthenticated with no HMAC/signature verification. The E2 review explicitly downgraded a HIGH finding on this exact endpoint to accepted-risk **on the binding condition that Wave D1 would land HMAC verification for it** — that condition was not met (D1 built HMAC only for its own new, separate `/webhooks/shopify` route). Per that review's own stated terms, this residual **re-escalates to HIGH**. Recommend: add signature verification to `ConversionWebhookController` before launch, following the exact precedent already proven twice (Shopify, WooCommerce) in this codebase. This is a bounded, well-understood fix, not new architecture — should not block the timeline materially.

**Condition 2 (should fix before RazorpayX disbursement is ever wired, not before this launch):** affiliate commission calculation trusts unbounded webhook order-amount with no sanity/upper-bound check. Non-blocking today because settlement is ledger-only (no real money moves per the D4 production gate), but must be closed before that gate is lifted.

All other tracked residual risks (Part D) are correctly scoped, correctly owned, and non-blocking for this specific launch — including E-JWKS (explicitly and correctly gated at E7, not E4) and the D5 backend follow-ups (UX completeness, not security).

**Recommendation to Arjun/Priya:** route Condition 1 to Vikram as a fast-follow before E7 (Swapnil's final approval) is requested — it is a real, if not new-this-session, gap that the existing documentation trail incorrectly implies is closed. Condition 2 should be logged against the same pre-disbursement checklist as the existing SETTLED-naming gate.
