## 1. Data/Model Choice — Meta Graph API usage

**Correct, and appropriately conservative.**

- `verifyInstagram` calls `InstagramInsightsClient.getMedia(igUserId, token, 50)` → `GET /{ig-user-id}/media?fields=...&limit=50`, then `getMediaInsights(mediaId, token, businessAccountId)` → `GET /{media-id}/insights?metric=impressions,reach,engagement,...`. Both are the correct, currently-supported Graph API endpoints for a Business/Creator IG account — there is no "look up media by shortcode/permalink" endpoint on this API (correctly documented in the class javadoc), so paging through recent media and matching on `permalink` is the only available approach, not a workaround hack.
- API version is centralized in `MetaGraphApiClient` (`BASE_URL + "/" + props.getGraphApiVersion()`), configured as `v25.0` (`MetaApiProperties.java:20`). Not deprecated as far as I can determine, but Graph API versions carry a ~2-year sunset window — **flag for Rohan/Vikram to add a calendar check against Meta's official deprecation schedule**, since this is a scheduled job that will fail silently (fallback, not crash) if the version ages out. This is a process gap, not a code defect.
- Reuses the exact same client (`InstagramInsightsClient`) already used by `MetricsPollingJob`/`InstagramMetricsFetcher` — no new API surface, no new permission scope requested (`instagram_basic` + `instagram_manage_insights`, both already in use elsewhere). Good: no incremental OAuth consent friction for creators.
- Field lists (`impressions,reach,engagement,saved,shares,video_views,likes,comments`) are the existing shared constant; verification only reads 3 of them (reach/impressions/engagement) — no new field surface added.

## 2. Integration

**Fits cleanly. One real (already self-flagged) gap for DPF-7 to inherit.**

- `DeliverableVerificationService` is invoked only by `DeliverableVerificationJob`, a `@Scheduled` sweep every 6 hours (cron offset 30 min from `MetricsPollingJob` — deliberate load-spreading, good). It is **not** wired into any creator-facing HTTP endpoint. This is a clean, low-risk integration choice: no request-path latency added to `markPosted`/`reportMetrics`, and it mirrors the existing `MetricsPollingJob` pattern the codebase already trusts.
- `DeliverableMetric.applyVerifiedReport` vs `applyReport` (self-report) has a correct one-way ratchet: once `source == PLATFORM_VERIFIED`, a later self-report (`applyReport`) leaves the numeric fields and `source` untouched (`DeliverableMetric.java:159-177`) — verified regressing to self-reported is structurally impossible, not just policy. Confirmed by test `verifiedRowResistsLaterSelfReportDowngrade`.
- `findByMilestoneId` is a 1:1 upsert target, so re-verification overwrites rather than duplicates (test `reVerificationOverwritesSameRowRatherThanAppending` covers this) — no double-counting risk for `DeliverableMetricService.getCampaignAnalytics`'s aggregate sums.
- **Known, already-documented gap (P1, inherited by DPF-7):** `DeliverableMetricService.getCampaignAnalytics` returns a single aggregate `CampaignAnalyticsResponse.source()` hardcoded to `SOURCE_CREATOR_REPORTED` (`DeliverableMetricService.java:199`, constant defined `AnalyticsDtos.java:31`) even when individual `deliverables[].source` rows are correctly `PLATFORM_VERIFIED` (per-row is correct, per `toResponse` reading `metric.getSource()` directly — `DeliverableMetricService.java:231-233`). This is self-flagged in `AnalyticsDtos.java:20-24` as intentional backward-compat, deferred pending a `MIXED` aggregate value. Not a DPF-6 defect since DPF-6 didn't create it, but it's a real integration seam: a brand's aggregate-level UI can display "CREATOR_REPORTED" for a campaign that in fact contains one or more platform-verified deliverables. **This is exactly the kind of thing DPF-7 (which is explicitly touching this file's gate logic) should close in the same pass** — recommend Vikram add a `MIXED`/derived aggregate `source` when `deliverables` contains a mix of both values.
- No conflict with `EscrowService`/release logic — javadoc explicitly states this service "never touches escrow/release logic (DPF-5, blocked separately)," and I confirmed no import or call from `verification/` into any escrow/milestone-release class. Correct scope discipline.

## 3. Anti-Gaming

Walking through all four sub-questions from the brief:

**(a) Can a creator submit a URL that verifies against someone else's post? No — closed by construction, not by a checkable rule.** `verifyInstagram` looks up the OAuth token strictly by `deliverable.getCreatorProfileId()` (`MetaOAuthTokenRepository.findFirstByCreatorProfileIdAndRevokedFalseOrderByCreatedAtAsc`), then calls `getMedia(creatorProfileId, ...)` — the `igUserId` path parameter passed to Meta *is* the deliverable's own creator. Meta's Graph API only returns media belonging to the IG user id you query with that user's own token; there is no parameter path by which a different creator's or a different IG account's media could be substituted. The shortcode is matched only within that returned set (`findByShortcode`). A creator physically cannot point verification at a post that isn't in their own account's recent-media page. Solid.

**(b) Can a stale/unrelated post match a cached shortcode? No new risk beyond what write-time validation already owns.** The shortcode comes from the `postUrl` string itself (parsed by `PostUrlIdentifier`, never from a cache), and `postUrl` was already validated once at write time (`CreatorDeliverableService#validatePlatformPostUrl`, DPF-3/3b) and is immutable per deliverable thereafter (single writer, per Kabir's DPF-3b note). There's no shortcode cache in this service — every sweep re-fetches recent media fresh. The only way a "wrong" post gets matched is if the creator posted, got a shortcode, deleted that post, then posted a *different* item that Instagram happened to reuse the exact same shortcode for — Instagram shortcodes are effectively unique/non-reused in practice, so this isn't a realistic vector.

**(c) TOCTOU / replay risk in the OAuth-token lookup? Low, and consistent with the rest of the codebase's Meta integration.** `getValidToken` is called once per verification attempt and the returned token is used for both the media-list call and the insights call within the same method invocation — no window where a revoked/rotated token could be swapped mid-flight beyond what `MetaTokenStorage` itself already guards (out of scope for this file — Kabir owns per the routing). No replay risk: this is a server-initiated, server-token GET, not a client-replayable request with creator-supplied auth material.

**(d) RECENT_MEDIA_LIMIT=50 silent-fallback gap — real, and this is my main finding (P1).** Confirmed: `DeliverableVerificationJob`'s `ELIGIBLE_STATUSES` is `{POSTED, METRICS_REPORTED}` and it re-sweeps every 6 hours *indefinitely* for any deliverable that hasn't reached `VERIFIED` — so a post that's currently outside the creator's most-recent 50 media items (an active creator posting frequently between the deliverable's post date and the sweep) will get `FALLBACK_NOT_FOUND` forever, silently, with **zero signal to the creator or brand that verification is failing** — there is no `verificationOutcome`/`lastAttemptReason` field anywhere in `Deliverable` or `DeliverableMetric`, and I confirmed by grep that `Outcome` never escapes `DeliverableVerificationService`/`DeliverableVerificationJob` (only appears in those 2 files + the log line). A brand looking at a deliverable will just see it permanently stuck on `CREATOR_REPORTED` with no visible reason, indistinguishable from "verification hasn't run yet." **Recommend:** persist the last `Outcome` + timestamp on `Deliverable` (or a small side table) and surface `FALLBACK_NOT_FOUND` specifically after N failed attempts as a distinct, brand-visible state ("could not verify — post may be outside recent history"), rather than an indefinite silent retry. This is a transparency/UX gap, not an exploitable anti-gaming hole — it doesn't let anyone fake a number, it just makes an honest failure invisible.

## 4. Cost

**Meta Graph API for Instagram Business/Creator insights has no per-call ₹ charge** — unlike an LLM API, this isn't metered billing; the constraint is Meta's *rate-limit budget* (Business Use Case Usage, tracked per business/IG account via the `X-Business-Use-Case-Usage` response header and pre-flight-checked in `MetaGraphApiClient.get` + `MetaRateLimitTracker`), not currency.

- **Per-verification cost:** 2 Graph API calls (`getMedia` + `getMediaInsights`), sharing the *same* rate-limit budget bucket as `MetricsPollingJob`'s existing polling for that creator (per-account limits are typically in the range of ~200 calls/hour per user token under Meta's standard tier — exact current cap should be confirmed against the live Meta dashboard rather than assumed). The pre-flight check in both `MetaGraphApiClient.get` (per-call) and `DeliverableVerificationService.verifyInstagram` (per-verification, `RATE_LIMIT_THRESHOLD_PERCENT = 90`) means this sweep degrades to `FALLBACK_RATE_LIMITED` rather than actually exhausting the shared budget or crowding out `MetricsPollingJob` — correct defensive design.
- **Abuse via repeated re-verification requests: not applicable — there is no creator-triggerable endpoint.** Verification only runs from the internal 6-hour cron sweep (`DeliverableVerificationJob`), with an `AtomicBoolean` overlap guard preventing concurrent runs. A creator has no way to force an out-of-cycle re-verification, so there's no "spam re-verify to burn rate-limit budget" attack surface today. **P2 note for later:** if a future task adds a manual "re-verify now" button (mentioned as a possibility in the job's own javadoc — "a future task can call `verify` synchronously"), that endpoint would need its own per-deliverable or per-creator rate limit independent of Meta's, since a malicious/careless creator could otherwise hammer it to burn the shared Meta rate-limit budget affecting other jobs (`MetricsPollingJob`) on the same account. Flagging now so it isn't missed when that follow-up is built.
- **Real dollar cost is infra, not API:** the sweep is O(all POSTED/METRICS_REPORTED deliverables) every 6 hours — negligible compute at current scale (this is a Sage/Influora-scale platform, not millions of rows), no external metered cost. No action needed today; revisit only if deliverable volume grows to where sweep duration approaches the 6-hour interval.

## Priya's XSS Render-Side Gate (DPF-3b carry-forwards) — COMPLIANCE CONFIRMED

Both hard constraints verified directly in code, not assumed:

- **(a) Never `decodeURIComponent`/`URLDecoder` on `postUrl`:** grepped `service/verification/` for `decodeURIComponent|URLDecoder|\.decode(` — zero matches in actual code (only a doc-comment mentioning the constraint by name in `PostUrlIdentifier.java:14`). `PostUrlIdentifier.extract` runs pure `Pattern.matcher(postUrl).matches()`/`.find()` against the raw string, never decodes.
- **(b) Reject encoded brackets/quotes at any render/logging point:** `PostUrlIdentifier.ENCODED_BRACKET` (`%3C|%3E|%22|%27|%60`, case-insensitive) is checked *first*, before any platform-pattern match, in `extract()` (`PostUrlIdentifier.java:51-57`) — a URL containing any of those sequences returns `Optional.empty()` immediately, which `DeliverableVerificationService.verify` turns into `FALLBACK_UNRECOGNIZED_URL` (line 134-140) and never proceeds to log or use the raw `postUrl` beyond that. Covered by test `encodedBracketInPostUrlIsSkippedEntirely`. Additionally confirmed **no log statement in this service ever logs the raw `postUrl` value** — both `log.info` (line 263) and `log.warn` (line 309, the fallback path) only log `deliverable.getId()`, the `Outcome` enum, a fixed reason string, and (on success) `platformMediaId` — never the URL itself. This is stronger than the minimum bar (avoids the log-aggregator-render-as-HTML class of XSS entirely, not just the two named vectors).

**Verdict on this gate: PASS, no violation, and implemented with one layer of defense-in-depth beyond what was strictly required** (log-scrubbing of `postUrl` wasn't explicitly demanded by Priya's ruling but closes an adjacent vector).
