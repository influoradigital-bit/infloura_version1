P1 MSA-01 BrandOwnContentService silently defaults Instagram auth path to FACEBOOK_LOGIN, reproducing the F-0950 class of bug on a code path F-0950 did not fix
Evidence E3 Confidence 78% Status OBSERVED Provenance COMMITTED
influora-api/src/main/java/com/influora/service/trendspark/BrandOwnContentService.java:112
Evidence: InstagramInsightsClient (integration/meta/client/InstagramInsightsClient.java:50-67) exposes both a 3-arg getMedia(igUserId, accessToken, limit) that hardcodes MetaAuthPath.FACEBOOK_LOGIN (line 62), and a 4-arg overload that takes the real auth path. PortfolioService.java:401 and DeliverableVerificationService.java:215/245 were fixed (per their own F-0950/F-0126 comments) to pass tokenRow.getAuthPath()/authPath explicitly. BrandOwnContentService.java fetches a real MetaOAuthToken at line 88-89 (which exposes getAuthPath(), used identically in MetaConnectionService.java:106) but at line 112 calls the 3-arg getMedia(igBusinessAccountId, accessToken.get(), RECENT_MEDIA_LIMIT) overload, never reading token.getAuthPath(). Any brand connected via INSTAGRAM_LOGIN (no linked Facebook Page) will have this call routed to graph.facebook.com and fail with Meta error 190 'Cannot parse access token' — the exact symptom PortfolioService's own comment describes for its pre-fix state.
Impact: TrendSpark's brand-own-content feature (BrandOwnContentService) is unusable for any brand onboarded via INSTAGRAM_LOGIN; only FACEBOOK_LOGIN-connected brands see their own content sync succeed.
Recommended fix: Change BrandOwnContentService.java:112 to call instagramInsightsClient.getMedia(igBusinessAccountId, accessToken.get(), RECENT_MEDIA_LIMIT, token.getAuthPath()).
Still needed to confirm: Runtime call against an INSTAGRAM_LOGIN-connected brand token, or a unit test mocking InstagramInsightsClient and asserting the 4-arg overload is invoked with the token's real authPath.
P2 MSA-02 Three scheduled jobs touching payment/financial-compliance data paths have zero test coverage
Evidence E3 Confidence 70% Status OBSERVED Provenance COMMITTED
influora-api/src/main/java/com/influora/job/IdempotencyReservationReaperJob.java; influora-api/src/main/java/com/influora/job/CreatorThemeTaggingJob.java; influora-api/src/main/java/com/influora/service/CampaignServiceInvoiceService.java:374 (retryFailedInvoiceFailures)
Evidence: grep -rl across influora-api/src/test/java for each class/method name returns zero hits for all three. Confirmed via `mvn -o surefire:test` against every job test class in src/test/java/com/influora/job (215/215 pass) plus EmailWorkerTest/PayoutReconciliationServiceTest/DeliverableVerificationServiceTest (42/42 pass) — none of these three units appears in any passing (or failing) suite because none exists. IdempotencyReservationReaperJob reclaims stuck idempotency-key reservations (a double-charge guard); CampaignServiceInvoiceService.retryFailedInvoiceFailures is the automated recovery path for GST Doc#2 invoices that failed to generate at escrow release (a documented compliance gap, F-0390 D1).
Impact: Both jobs are wired, compiled, cron-scheduled and @SchedulerLock-protected (infra is sound) but their actual per-row logic has never been exercised by any test — a regression in either would not be caught by `mvn test` today.
Recommended fix: Add a dedicated *JobTest for IdempotencyReservationReaperJob and CreatorThemeTaggingJob, and a CampaignServiceInvoiceServiceTest covering retryFailedInvoiceFailures's PDF_RENDER and invoice-create retry branches.
Still needed to confirm: New unit tests plus a review of whether the missing tests reflect an intentional scope cut or an oversight.
