# Answers: F-0625 & F-0629 (Contract Signature Dashboard + Deal Room Links)

Test evidence for every claim below: I ran the four real test files that cover these two areas —
creator-dashboard.unsigned-contracts.test.tsx, creator-chat-unmatched-deal-id.test.tsx,
creator-dashboard.test.tsx and creator-chat-refresh.test.tsx — with npx vitest run.
Result: 4 files passed, 16 tests passed, 0 failed. I then falsified the two guards these
questions are about by reverting each one in place and re-running: 4 tests went red (3 milestone
cases plus the unmatched-id case) and only those, then I restored both files and re-ran to green.
The restore is verified — git diff on creator-chat.tsx is empty and the milestone guard is back
on its line.

### 1. What happens when the "Contracts awaiting your signature" section renders a contract that has zero milestones in the backend response?

It renders the row normally with a count of 0 and does not crash. The count is read through an
optional-chain plus nullish-coalesce guard, so an empty array, an absent key, an undefined and a
null all land on the same fallback of 0 and the row keeps rendering its amount and its
brand-signed caption. This genuinely works and is genuinely tested — three it.each cases assert
it, they pass, and they fail when I remove the guard. The one honest limitation is that a
contract with a real empty milestone schedule and a contract whose milestones field never arrived
render identically as 0 milestones; the UI cannot tell those apart.
`src/pages/creator-dashboard.tsx:573` "contract.milestones?.length ?? 0"

### 2. What happens when a contract in the dashboard list has a `null` or `undefined` value for a required field (e.g., `brandName`, `campaignTitle`, `contractId`) — does the UI crash, render blank, or show a fallback?

There is a real gap here, and it is bigger than a null-handling question. brandName and
campaignTitle are never rendered on these rows at all — the row shows only the formatted rupee
total, the milestone count, and a brand-signed caption. A creator with three unsigned contracts
sees three visually identical rows distinguishable only by amount, with no brand and no campaign
name to tell them apart. For the fields that are used: a null totalAmount is safe because
formatINR returns a neutral em dash rather than a rupee NaN; a null id costs only a React key
warning; a null or undefined collaborationId is the one that bites, because it is interpolated
straight into the href with no guard, producing a link to the literal string undefined that
dead-ends on the deal room empty state. No test in either file covers a null or undefined on any
of these fields — the regression suite covers milestones only.
`src/pages/creator-dashboard.tsx:562` "contract.collaborationId"

### 3. When a creator clicks a contract row in the dashboard, and the `contractId` in the URL is valid but belongs to a *different* creator, does the deal room show that other creator's contract data, return a 403, or fail in another way?

Neither the other creator's data nor a 403 — it fails closed on the frontend before a request is
even made, and would 404 on the backend if one were made. The deal room never sends a
URL-supplied id to the contract endpoint: the id it fetches comes off the already-resolved
selected deal, and that deal is resolved by matching the URL id against the creator's own
server-scoped deal list, so a foreign id matches nothing and the page shows the no-deals screen.
On the backend, the creator-scoped read is an ownership-scoped repository lookup keyed on the
authenticated user id, which throws CONTRACT_NOT_FOUND as a 404 rather than a 403. Both layers
hold independently. Neither of the two test files exercises the cross-creator case; the backend
half is covered by its own service tests, the frontend half only implicitly by the unmatched-id
test.
`influora-api/src/main/java/com/influora/service/ContractService.java:1050` "findByIdAndCreatorId(contractId, creatorUserId)"

### 4. When a creator follows a dashboard link to `/creator-chat?dealId=X` but that deal or contract no longer exists (deleted, or the creator was removed from it), what does the UI display?

Two corrections to the premise first: the route is /creator/chat and the parameter the dashboard
emits and the page reads is deal, not dealId. With that spelling, an explicitly requested id that
matches nothing resolves to null and the page renders its no-deals screen — never a substituted
deal. That part works and is falsified by test. What is not right is the copy: the screen a
creator lands on is the generic first-run empty state telling them brands they are talking to
will show up here as deal rooms. For a creator who has five other live deals and just followed a
stale contract link, that statement is false and gives no hint that the link was the problem.
This is the empty-state-misleads defect class the codebase keeps hitting, applied to a
deep-link failure rather than a fetch failure.
`src/pages/creator-chat.tsx:1851` "will show up here as deal rooms"

### 5. When a dashboard contract link is followed with a *malformed* or *non-numeric* `dealId` or `contractId` parameter, does the deal room page crash, show an error boundary, or gracefully handle the invalid input?

It handles it gracefully, and there is nothing to crash on: ids in this system are strings, not
numbers, and the URL value is only ever compared for string equality against the creator's deals.
Nothing parses it, so there is no NaN path and no error boundary is involved. A malformed value
behaves exactly like a stale one — the no-deals screen. One genuine fragility, which is the
question's own spelling: a parameter literally named dealId is not read at all, so a link like
/creator/chat?dealId=99999 leaves the requested-id state null, which takes the
nobody-asked-for-anything branch and silently mounts the creator's first deal room. Nothing in
the product emits that spelling, but a hand-edited or mis-copied link lands on an unrelated deal
with no indication anything was ignored.
`src/pages/creator-chat.tsx:781` "selectedDealId == null"

### 6. If the API returns a contract with milestones but one milestone object is missing a required field (e.g., `amount`, `description`, `deadline`), does the contract detail view in the deal room render correctly, partially, or throw an error?

It cannot throw, because the deal room does not render milestones at all. The contract panel is
handed only a contract id, brand name, campaign name, deal amount, the server-summed contract
total and a status — there is no milestones prop, and across every creator deal-room component
the word milestone appears only inside comments. So a malformed milestone object is inert here.
The flip side is a real product gap rather than a crash risk: the creator is asked to countersign
a contract whose milestone schedule — the amounts, descriptions and deadlines they are agreeing
to — is never shown to them anywhere in the deal room; the dashboard row's bare count is the only
place milestones surface in this whole flow.
`src/pages/creator-chat.tsx:2856` "selectedDeal.brandName"

### 7. When a creator refreshes the deal room page (`/creator-chat?dealId=X`) directly (not via dashboard navigation), does it correctly fetch and display the contract, or does it rely on in-memory state that is now missing?

It refetches everything; there is no in-memory handoff from the dashboard. The requested id is
read from the query string at mount and seeded into state there, the deal list is loaded from the
API by a mount effect, and the contract itself is fetched from the resolved deal's contract id by
its own effect — a cold load and a navigated load take the identical path. This is tested for
real: creator-chat-refresh.test.tsx mounts the page cold from a router entry carrying the deal
parameter and asserts the named deal's room is on screen, and it passes.
`src/pages/creator-chat.tsx:676` "const dealId = searchParams.get"

### 9. Is there a falsified test that *starts* with an invalid `dealId` (e.g., `dealId=99999` or `dealId=abc`), navigates to `/creator-chat?dealId=99999`, and asserts the page shows an error state (not a crash, not someone else's data)?

Yes in substance, with two honest caveats. creator-chat-unmatched-deal-id.test.tsx starts from a
router entry carrying an unmatched id, with two real deals loaded so a silent substitution has
something to substitute, and asserts the no-deals screen is shown and that neither real campaign
name appears — which is exactly the not-someone-else's-data half. It is falsified: restoring the
old first-deal fallback makes it fail, and I ran that revert myself. Caveat one, what it asserts
is the empty state, not an error state, because the page has no error state for this case — see
question 4. Caveat two, it uses the parameter name the app actually reads, so the dealId spelling
in this question remains untested and, as noted in question 5, is silently ignored by the page.
`src/pages/creator-chat-unmatched-deal-id.test.tsx:100` "deal=stale_or_wrong_id_123"

### 10. When the dashboard link transitions to the deal room, is the `dealId` or `contractId` parameter validated against the logged-in creator's identity on the backend before returning contract data, or does the frontend assume the API will never return unauthorized data?

It is validated on the backend, and the frontend does not rely on that alone. The unsigned list
endpoint rejects any non-creator principal outright and then queries strictly by the
authenticated creator's own user id; the single-contract read resolves through an
ownership-scoped lookup; and the deal read the room depends on goes through an owned-collaboration
check. Independently, the frontend never forwards a URL-supplied id to an API call — it filters
the id through the creator's own scoped deal list first — so an unauthorized id is dropped client
side before any request leaves the browser. This is the one part of this flow where both layers
are genuinely correct and neither is trusting the other.
`influora-api/src/main/java/com/influora/web/ContractController.java:61` "principal.getUserType() != UserType.CREATOR"
