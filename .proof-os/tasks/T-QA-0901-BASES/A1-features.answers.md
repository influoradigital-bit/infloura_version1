### 16. What are the campaign statuses defined in the code, and which transitions are legal?
Six statuses exist in the enum: DRAFT, PENDING_APPROVAL, ACTIVE, PAUSED, COMPLETED, CANCELLED. There is no transition table or state machine anywhere in the backend — the PATCH handler simply takes whatever status the client sends and assigns it, so any status can be set from any other. The only real guards are three independent checks: COMPLETED and CANCELLED cannot be patched at all, a move to ACTIVE requires a VERIFIED workspace, and only DRAFT can be deleted. So, for example, ACTIVE back to DRAFT or PENDING_APPROVAL straight to COMPLETED are both accepted today.

### 19. What is a HYPE campaign and how does it differ from a standard campaign in the model?

### 30. How are campaign deliverable requirements defined and stored?

### 31. What is the difference between a Deal and a Collaboration in the data model?
There is no Deal entity at all — the entity package contains Collaboration.java but no Deal.java, and a deal is simply the REST vocabulary the frontend uses for a Collaboration row plus its DealMessage timeline. DealController maps /deals onto Collaboration, so a deal id IS a collaboration id everywhere in the API. Collaboration holds campaignId, creatorId, status, source, agreedRate, currency, notes and usageRights; the negotiation history and offer cards live in the separate deal_messages table. Contract, EscrowHold and PaymentMilestone all hang off collaborationId, never off a deal id.
