## 2b. F-0652 — request-level idempotency on release/refund → **NOT FIXED**

This is the one I would block the wave on.

**The mechanism is correct.** It reuses `IdempotencyService.executeOnce` — the same shared
building block the webhook paths and `WalletService#requestCreatorWithdrawal` use, with its
insert-first-wins DB constraint (`IdempotencyService.java:1-60, 100-140`). It is **not** a parallel
bespoke mechanism. Citations: `EscrowService.java:125` (`@Autowired private IdempotencyService idempotencyService`),
`:1077-1101` (`withRequestIdempotency`), `:1103-1120` (`currentReleaseStatusByMilestone`, the
non-locking replay read).

**And re-execution genuinely is skipped, not coincidence.** I specifically checked the trap you
named. `EscrowServiceIdempotencyTest` stubs `findByIdForUpdate` to return **two distinct FUNDED
`EscrowHold` instances**, then asserts after the second call that `writeSnapshot2.getStatus() ==
FUNDED` — i.e. the second, independent, still-releasable snapshot was never touched. That is a
direct assertion that the write path did not run twice; it is not "the same result by luck of the
ledger-level dedup", because the second snapshot would have been released if the write path had run.
`verify(escrowBackend, times(1)).release(any())` backs it. 3/3 pass.

**But it is dead code.** The new overloads have **zero production callers**:

| Route | Controller line | Calls |
|---|---|---|
| `POST /wallet/escrow/release` (milestone) | `web/EscrowController.java:122` | `escrowService.release(principal, workspaceId, milestoneId)` — **3-arg, no key** |
| `POST /wallet/escrow/release` (hold) | `web/EscrowController.java:125` | `escrowService.releaseByHoldId(principal, workspaceId, escrowHoldId)` — **3-arg, no key** |
| `POST /wallet/escrow/refund` | `web/EscrowController.java:146` | `escrowService.refund(principal, workspaceId, escrowHoldId)` — **3-arg, no key** |

`EscrowController.java` is **not modified** in this working tree. `/release` and `/refund` declare no
`@RequestHeader("Idempotency-Key")` at all (only `/fund` does, at `:71`). A `grep` for callers of the
4-arg overloads across `src/main` returns nothing.

F-0652's symptom is *"a duplicated caller request to release/refund has no request-replay key"*.
After this change, a duplicated caller request to release/refund **still has no request-replay key**,
because no HTTP request can reach the code that would consume one. The finding is unchanged in
production; only an unreachable overload and a unit test were added.

**To actually close it:** add `@RequestHeader(value = "Idempotency-Key", required = false)` to
`EscrowController#release` and `#refund` and forward it to the 4-arg overloads (the
`DealController.java:90/98/108` pattern), then set the header client-side in `src/lib/api.ts`.
Until then this is BUILT, not FIXED.

**Secondary note (F-0406 rider, not blocking):** the same diff narrows `isExpectedReleaseSkip`
(`EscrowService.java:838-845`) so `MILESTONE_NOT_FOUND` / `ESCROW_NOT_FOUND` /
`COLLABORATION_NOT_FOUND` now throw out of `tryReleaseOnApproval` and roll back `approve()`. I read
that carefully because it changes a money path's failure mode: it is correct and well-argued, the
four retained "held" codes are genuinely self-resolving states, and `EscrowServiceReleaseOutcomeTest`
covers all three loud branches plus the retained `MILESTONE_NOT_FUNDED` held branch (6/6 pass).

## 3. F-0644 — analytics double-count across contract versions → **FIXED, BUT INTRODUCES A WORSE DEFECT**

**Citation:** `influora-api/src/main/java/com/influora/service/DeliverableMetricService.java:187-214`.

**Is it genuinely contract-version-scoped, not a status flag that happens to work today?** Yes —
this part is right. Line 200 filters on `currentContractIds.contains(m.getContractId())`, i.e. on the
actual `payment_milestones.contract_id` FK (`PaymentMilestone.java:27-28`, `nullable = false`, so no
silent null-drop), and line 213 filters metrics through `currentMilestoneIds` derived from that same
set. It is not a `MilestoneStatus` proxy. Good.

**But the definition of "current" is wrong, and it disagrees with the F-0645 fix in the same diff.**

Line 187-197 resolves the current contract as
`findByCollaborationIdOrderByVersionDescCreatedAtDesc(id).stream().findFirst()` — i.e. **the newest
row, unconditionally, including an unsigned DRAFT amendment**. The javadoc at `:180-186` claims this
is "the same ... lookup `DealService#toDealResponse` relies on". **That claim is false as of this
same working tree**: `DealService.java:2034` was changed in this very wave to call
`resolveCurrentContract(contracts)` (`:2122-2136`), which deliberately does **not** take
`contracts.get(0)` when the newest is DRAFT/PENDING_SIGNATURES. Two services in one diff now hold two
different definitions of "the current contract", and the newer one's comment cites the older
behaviour of the other.

**Consequence — proven by their own test, not by my speculation.**
`DeliverableMetricServiceTest.testAnalyticsScopesToCurrentContractVersionAfterAmendment`
(`:168-209`) constructs exactly the F-0645 scenario: v1 `ACTIVE` with two milestones (one **`RELEASED`**
— money already paid, work already delivered, metrics already reported: reach 1000 + 2000) and v2
**`DRAFT`** with one milestone (reach 300). It then asserts:

```java
assertEquals(1, response.deliverablesTotal());
assertEquals(300L, response.totalReach());
```

So the moment a brand *drafts* an amendment — before anyone signs it, and even if it is never signed —
campaign analytics **silently discard every already-delivered, already-paid milestone and its
reported metrics**. Reach goes 3300 → 300. That is not a smaller error than double-counting; it is
the erasure of the real, settled history, in the direction that makes a campaign look like it
under-delivered.

**Verdict: FIXED for the stated symptom, but ships a regression I would not sign off.** The filter
must resolve "current" through the same rule `DealService.resolveCurrentContract` uses (prefer the
ACTIVE predecessor while the newest is unsigned), or — better for an *aggregate* — count the union of
every non-CANCELLED contract version's milestones while de-duplicating, since a released milestone on
a superseded version is real delivered work that belongs in campaign totals.

**Minor, non-blocking:** `:187-197` issues one `contractRepository` query **per collaboration** inside
a stream, on a read path (N+1). A campaign with 200 collaborations = 200 queries. Batch it.

## 4. F-0645 — funded escrow vs current contract after amend → **PARTIAL (defers the break, does not close or surface it)**

**Citations:** `DealService.java:2034` + `:2091-2136` (`resolveCurrentContract`),
`ContractService.java:441-520` (`amend`), `:507-510` (predecessor handling),
`Contract.java:211-217` (`advanceIfFullySigned`), `:243-245` (`canCancel`).

**What is genuinely honest now.** While the amendment is unsigned, `resolveCurrentContract` keeps
surfacing the **ACTIVE, funded predecessor** as `contractId`/`contractStatus`, so the response no
longer shows `contractStatus=DRAFT` beside `escrowFunded=true`. The funded↔current relationship is
therefore **preserved** during that window, which satisfies the finding's first branch. The amendment
is not hidden — `GET /contracts?dealId=` still returns every version. `DealServiceTest`
`testGetKeepsFundedActiveContractCurrentWhileAmendmentDraftIsUnsigned` proves it, and all 68
`DealServiceTest` cases pass.

**What is still silent, and why I cannot call this FIXED.**

1. `ContractService.amend` (`:507-510`) cancels the predecessor **only** when `canCancel()` — i.e.
   DRAFT/PENDING_SIGNATURES. An **ACTIVE** predecessor is deliberately left ACTIVE. And I verified
   nothing anywhere else ever moves a Contract off ACTIVE: `setStatus(...)` has exactly two call
   sites in `src/main` (`ContractService.java:508` and `:942`, both → `CANCELLED`), and
   `ContractStatus.COMPLETED` is never assigned anywhere.
2. Therefore, once the amendment is signed, `advanceIfFullySigned()` makes v2 ACTIVE while **v1 is
   still ACTIVE**. `resolveCurrentContract` sees a non-unsigned newest and returns v2 (`:2129-2131`).
3. `escrowFunded` is computed collaboration-scoped, not contract-scoped
   (`hasEscrowForCollaboration`, `DealService.java:2041-2043`), so it stays `true`.
4. Net: the response now says *"current contract = v2, escrow funded = true"* while the FUNDED hold is
   still bound to **v1's** milestone. That is the exact F-0645 symptom — the funded/current link broken
   silently — just moved from "during the amendment window" to "from the moment the amendment is signed,
   permanently".

**The test does not cover this.** `testGetSurfacesNewestContractOnceAmendmentIsSigned`
(`DealServiceTest`, the "amendment signed" case) builds v1 as **`CANCELLED`** — a state
`amend()` provably cannot produce for an ACTIVE predecessor (`:507`, `canCancel()` excludes ACTIVE).
So the one post-signature state that `amend()` can actually create is untested. I want a test at
`(v1 ACTIVE, v2 ACTIVE, escrowFunded=true)` asserting the response is honest about which version the
money is on — today it is not.

**To close:** either carry escrow forward to the new version's milestones on amendment-signature, or
add an explicit field (a `pendingAmendmentId` / `fundedContractId`) so the split is *stated* rather
than resolved by picking a winner.
