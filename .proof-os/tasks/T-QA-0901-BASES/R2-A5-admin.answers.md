### 1. `AdminContextService.requireMfaSatisfied` checks `admin.isMfaEnabled()` on every privileged call, and `AdminAuthService`'s class javadoc states role/MFA state is deliberately NOT carried in the JWT. Once an admin has enabled MFA once, does any later request ever force a fresh TOTP challenge again, or does a bare valid access token forever satisfy the MFA gate for the life of the account?
A bare valid access token forever satisfies the gate. requireMfaSatisfied is a persistent-boolean check against the admin_users row, not a per-session proof of possession: it only asks whether mfaEnabled is true, and there is no mfa-verified-at timestamp on the session, no MFA claim in the JWT, and no re-challenge anywhere in the admin controllers. A fresh TOTP code is demanded exactly once per login, inside AdminAuthService.login; every request made with the resulting access token, and every access token minted by the refresh rotation afterwards, passes the MFA gate without another code.

### 2. `AdminAuthService.login` enforces MFA-required-at-login for `SUPER_ADMIN`/`ADMIN` only when `AdminSecurityProperties.isMfaEnforceOnLogin()` is true. ### 3. `AdminAuthController.refresh` reads the refresh token from the HttpOnly cookie first and falls back to a request-body token only when the cookie is absent. ### 6. `AdminAuthService`'s lockout increments `failed_login_attempts` on both a wrong password AND a wrong MFA code, sharing one counter and one cooldown window (`AdminSecurityProperties`). Does a `SUPER_ADMIN` who repeatedly mistypes their TOTP code (e.g. a stale app) get locked out of the account by the same threshold as a brute-force password attacker, and is there any in-app way to clear that lockout before the cooldown expires?
The shared-counter premise is false. A wrong MFA code routes to recordFailedMfaAttemptAndThrow, which increments a separate MFA counter with its own budget, while a wrong password routes to recordFailedAttemptAndThrow against failed_login_attempts. A stale authenticator therefore locks the account after 3 attempts for 1 hour, versus the password path's 5 attempts for 15 minutes — strictly harsher, not the same threshold. There is no in-app unlock: no admin-management endpoint exists, and both counters clear only on a successful login or by waiting out the cooldown.
