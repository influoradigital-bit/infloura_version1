## 1. F-0489 — release control for a milestone-less FUNDED hold — **FIXED**

### Wire shape (never both, never neither)

`src/lib/api.ts:3628-3641` — `releasePayout(request: string | { escrowHoldId: string })`.
The body is built as a single ternary at **`src/lib/api.ts:3634`**:

```ts
const body = typeof request === 'string' ? { milestoneId: request } : { escrowHoldId };
```

One branch, one key. It is structurally impossible to emit both. The "neither" case is
guarded at **`src/lib/api.ts:3631-3633`** — an object variant with a falsy `escrowHoldId`
throws before `fetch` is reached, rather than posting `{ escrowHoldId: undefined }` (which
`JSON.stringify` would drop, producing the empty-body 400).

Matches the server contract I read independently — `EscrowController.java:111-125` computes
`hasMilestone` / `hasHold` and rejects unless exactly one is present; `MoneyDtos.java:218`
`EscrowReleaseRequest(String milestoneId, String escrowHoldId)`.

Existing per-milestone caller is untouched: `deal-payments-tab.tsx` still passes a bare string,
and `npx tsc --noEmit` exits **0** across the repo, so the widened signature broke no caller.

### Reachability of the control

`src/pages/brand-wallet.tsx:1605-1616` renders the button under
`row.status === 'FUNDED' && !row.milestoneId`, calling `handleReleaseHold`
(**`src/pages/brand-wallet.tsx:530-551`**) → `api.payments.releasePayout({ escrowHoldId })`.

I checked the two ways this could be a dead control and neither applies:

- `milestoneId` is a **real** field on the wire, not an FE-only invention (the failure mode in
  memory `feedback_fe_type_asserts_missing_dto_field`). `GET /wallet/escrow`
  (`EscrowController.java:58-66`) returns `EscrowStatusResponse`, and
  `EscrowService.java:1729-1740 toStatusResponse` maps `hold.getMilestoneId()` through. It is
  neither hardcoded null (which would put the button on every hold) nor absent (which would put
  it on none). `@JsonInclude(NON_NULL)` on the record means a null milestone is omitted, which
  the `!row.milestoneId` check handles identically.
- The button is a real `<Button onClick=…>`, not a div styled as one (memory
  `feedback_dead_controls_invisible_to_static_checks`) — and the vitest below actually clicks it.

`releaseByHoldId` exists on the server side: `EscrowService.java:597-602`.

### Residual (non-blocking, not a defect in this fix)

- No client-side role gate. `EscrowService.releaseByHoldId` requires `OWNER`/`ADMIN`
  (`EscrowService.java:599-600`), so a brand `MEMBER` sees a Release button that always 403s.
  The server refusal is surfaced verbatim by the toast, which is a defensible choice and
  consistent with the milestone control, but it is a dead-control-shaped UX for that role.
- `EscrowHoldRow['status']` (`src/lib/api.ts:3165`) has no `FROZEN` member, though
  `EscrowService` freezes holds on dispute. A frozen hold falls into the badge `default` branch
  and correctly shows no button, so this fix is safe — but the union is stale. Separate ticket.

## 2. F-0648 — `resetMfaForAdmin` revokes the target's refresh tokens — **FIXED**

`AdminAuthService.java:349-353` (post-diff numbering) — the method body:

```java
AdminUser target = loadActive(targetAdminId);
target.resetMfa();
adminUserRepository.save(target);
adminRefreshTokenRepository.revokeAllForAdmin(target.getId());   // ← F-0648
```

The revocation is **unconditional** — it sits below the `loadActive` call with no role branch
above it, so it applies identically to a `SUPER_ADMIN`, `ADMIN` and `SUPPORT` target. That is
the whole point: `SUPPORT` is exempt from `AdminContextService#requireMfaSatisfied`, so before
this line a `SUPPORT` reset had *zero* session-side effect.

The mechanism is real, not a stub — `AdminRefreshTokenRepository.java:15-18`:

```java
@Modifying(clearAutomatically = true)
@Transactional
@Query("UPDATE AdminRefreshToken t SET t.revoked = true WHERE t.adminId = :adminId AND t.revoked = false")
void revokeAllForAdmin(@Param("adminId") String adminId);
```

and the refresh path only accepts unrevoked rows (`findByTokenHashAndRevokedFalse`,
`AdminRefreshTokenRepository.java:13`), so a revoked token genuinely cannot be exchanged.
It is scoped by `target.getId()`, i.e. the target, not the caller — and the caller/target ids
must differ, since `AdminAuthService.java:343-348` rejects a self-reset before this point.

The endpoint is reachable, not orphaned: `AdminAuthController.java:135-140`
`@PostMapping("/mfa/reset/{targetAdminId}")` → `adminAuthService.resetMfaForAdmin(...)`.

### Tests — I ran them

```
cd influora-api && mvn -o clean -Dtest=AdminAuthServiceTest,ProvisionSuperAdminRunnerTest -DfailIfNoTests=false test
→ com.influora.service.admin.AdminAuthServiceTest — Tests run: 5, Failures: 0, Errors: 0
```

Both required targets are covered and both assert on the target id, not the caller id:
`resetMfaRevokesTargetsRefreshTokens_superAdminTarget` and
`resetMfaRevokesTargetsRefreshTokens_supportTarget`, each
`verify(adminRefreshTokenRepository, times(1)).revokeAllForAdmin(TARGET_ID)`. Pre-fix the line
did not exist, so both assertions fail on the pre-fix tree by construction — these are
inherently falsifying assertions, not decoration.

### Residual (accepted, worth stating)

Already-issued **access** tokens for the target stay valid until natural expiry — only refresh
tokens are revoked. That is standard and matches `logout`'s existing behaviour, so the
containment window equals the access-token TTL rather than zero. Not a defect in this fix.

## 3. F-0650 — atomic check-then-insert in `ProvisionSuperAdminRunner` — **NOT FIXED**

The named lock is real and its ordering is correctly implemented **inside the JVM**. It is not
atomic **against the database**, and the class javadoc asserts a property the code does not have.

### The defect

`ProvisionSuperAdminRunner.java:190-195`:

```java
int provisionAdmin(String email, String password) {
    Integer exitCode = transactionTemplate.execute(status -> provisionAdminLocked(email, password));
```

`releaseBootstrapLock()` runs in the `finally` **inside** the callback
(**`ProvisionSuperAdminRunner.java:255-260`**), i.e. while the transaction is still open. The
transaction commits only after the callback returns, back in `provisionAdmin` at line 191.
MySQL named locks are not transactional — `RELEASE_LOCK` takes effect the instant it executes.

The class javadoc at **`ProvisionSuperAdminRunner.java:91-94`** claims the opposite:

> "…proceeds through count+insert and releases the lock **only once its row is durably
> committed**; the second process blocks on `GET_LOCK` until the first releases, then runs its
> own `count()` against the now-committed row…"

The code does the reverse: release, *then* commit. This is exactly the "decorated with a comment
claiming so" case.

### Why the window is not theoretical here

It is worse than a commit-duration race, for two compounding reasons:

1. **The INSERT has not even been issued when the lock is released.** `AdminUser` uses an
   assigned id — `AdminUser.java:29-31` is a bare `@Id` `String` with no `@GeneratedValue`, and
   the id comes from `Ulids.newUlid()` at `ProvisionSuperAdminRunner.java:228-230`. Spring Data's
   `save()` on a new entity calls `persist()`, which for an assigned identifier defers the INSERT
   to flush/commit. So at `RELEASE_LOCK` time the row exists only in the persistence context. The
   race window spans the entire flush **plus** commit round-trip, not just the commit.

2. **The loser is woken directly into that window.** Process B is parked on `GET_LOCK` for the
   whole of A's run and resumes at the exact moment A releases — then immediately runs `count()`
   while A has still not flushed. For the one scenario this fix exists for (two operators
   launching the script concurrently), the second process is *maximally* likely to land in the
   window, not least likely. `count()` is a consistent read and cannot see A's uncommitted row,
   so B sees 0, inserts, and `admin_users` ends up with two `SUPER_ADMIN` rows under two
   different emails — the original F-0650 outcome, since the only UNIQUE constraint is on email.

The lock does narrow the race substantially versus the pre-fix code. It does not close it, and
the fix is documented as closing it.

### Why their test suite cannot see this

`ProvisionSuperAdminRunnerTest.twoConcurrentInvocationsProduceExactlyOneAdminRow` backs the
mocked `save()` with `rowCount.incrementAndGet()` — an **instantly visible** write. The harness
therefore models a database in which the insert is durable the moment `save()` returns, which is
precisely the assumption that is false. The suite cannot fail on this defect no matter how the
threads interleave. Its own javadoc's "What this does NOT prove" section is honest about MySQL
semantics and cross-process runs, but does not name this gap.

### Tests — I ran them

```
cd influora-api && mvn -o clean -Dtest=ProvisionSuperAdminRunnerTest -DfailIfNoTests=false test
→ Tests run: 6, Failures: 0, Errors: 0
```

Green, and (per the probe below) genuinely sensitive to the lock's scope — just blind to the
commit boundary.

### Suggested fix

Make the check-and-insert one statement so no lock is needed and no commit boundary matters, e.g.
a native `INSERT INTO admin_users (…) SELECT … WHERE NOT EXISTS (SELECT 1 FROM admin_users)` and
branch on the affected-row count. That stays inside this file's boundary (no migration, no new
repository method) and is atomic by construction. If the named lock is kept, the release must
happen *after* commit and on the same connection — which the current `TransactionTemplate` shape
cannot express, so the single-statement route is the cheaper correct answer.

## 4. Revert probe (my own) — run against F-0650

I chose F-0650 because it is the item whose test does the most work and therefore had the most
room to be self-greening.

**Probe design.** A naive revert (delete the lock entirely) would fail the suite for the wrong
reason — Mockito strict stubs would raise `UnnecessaryStubbingException` on the now-unused
`GET_LOCK` stubs, which proves nothing about concurrency. So I kept `GET_LOCK` and
`RELEASE_LOCK` being called, and only moved the release so the lock no longer *covers* the
critical section: `releaseBootstrapLock()` before `count()`, `finally` block emptied. If the
suite were decoration (merely asserting the lock calls exist), it would stay green.

**Result — it failed, and on the substantive assertion:**

```
[ERROR] ProvisionSuperAdminRunnerTest.twoConcurrentInvocationsProduceExactlyOneAdminRow:316
        exactly one invocation must succeed ==> expected: <1> but was: <2>
[ERROR] ProvisionSuperAdminRunnerTest.acquiresLockBeforeCheckingAndReleasesAfterInserting:204
[ERROR] ProvisionSuperAdminRunnerTest.releasesLockWhenAbortingOnExistingRow:224
[ERROR] Tests run: 6, Failures: 3, Errors: 0
```

Two rows created, exactly the F-0650 symptom. So the concurrency test is a real proof of the
in-JVM acquire → check → insert → release ordering. It is not a real proof of atomicity against
the database, for the reason in §3.

**File restored** — `grep -c "PRIYA REVERT PROBE"` returns 0 and the suite is green again
(`Tests run: 6, Failures: 0`). The working tree is byte-identical to what I received.
