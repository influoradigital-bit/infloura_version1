# F-0448 Answers — GET/PATCH /users/me Routes

Read fresh from the code on 2026-09-04. The ledger claim (likely dead code, no frontend caller) is

### 1. Where in the shipped frontend bundle (production build) does a call to GET /users/me or PATCH /users/me appear, if anywhere?

Two places. The API layer defines both calls in the users export, and exactly one page consumes
them: the brand Settings page. That page is a static (non-lazy) import in the router, so it lands in
the main production chunk, not a split chunk that might never load. Both calls pass the brand token
role, so the paths are emitted into the bundle unconditionally in live mode.

`src/App.tsx:315` "<BrandSettingsPage />"

### 2. What UI component or screen triggers a GET /users/me request, and under what user action does that request fire?

BrandSettingsPage triggers it from a mount effect, not from a user action. The loader is a
useCallback with an empty dependency list, run by an effect that fires once when the page mounts —
before the user opens the Security tab where the data is actually shown, and with no live/mock guard
(mock mode resolves a canned object instead). The only user action that re-fires it is the Retry
button rendered in the error branch of the Mobile Number card.

### 3. When the UI component that calls GET /users/me first renders, does it display data from that fetch response, or does it show a value already present in local state or props?

It displays data from the fetch. The saved-phone state starts null and the loading flag starts true,
so the first paint is a Loading line, and the number only appears after the response resolves — the
component reads the phone straight off the response object. There is no props or auth-store fallback
for this field. The one caveat is mock mode, where the same code path resolves a hard-coded seed
number that is rendered as if it were the account's real number.

### 4. What specific user-editable fields are bound to the PATCH /users/me endpoint, and what screen are they visible on?

Exactly one field: the account mobile number, on Brand Settings, Security tab, Mobile Number card,
edited through a dialog. The request body sent is only the normalized phone. The other five fields
the backend accepts on this endpoint — firstName, lastName, displayName, timezone, avatarUrl — have
no caller anywhere in the frontend; they are typed in the payload interface and applied server-side,
but no screen binds an input to them, so they are reachable only by a hand-crafted request.

### 5. When a user submits a form or action that triggers PATCH /users/me, what visible feedback does the UI show on success (toast, redirect, inline message, field update, etc.)?

Three things, all in the success branch of the save handler: the card value is replaced with the
phone echoed back by the response, the dialog closes, and a success toast fires. No redirect, and no
re-fetch of GET /users/me — the card trusts the PATCH response body.
`src/pages/brand-settings.tsx:309` "Mobile number updated"

### 6. What distinct HTTP error responses can PATCH /users/me return (400, 401, 403, 409, 500, etc.), and what does the UI display for each?

400 INVALID_PHONE (non-blank value that fails the Indian-mobile rule) and 400 PHONE_REQUIRED (a
BRAND caller sending a blank string) and 409 PHONE_ALREADY_EXISTS (pre-check, plus a
DataIntegrityViolation catch on the unique column) all get their own inline message next to the
field, because the handler branches on the machine-readable code rather than on the status. 404
USER_NOT_FOUND falls through to a generic destructive toast. A 401 gets one silent refresh-and-retry
inside the HTTP client; if the refresh fails the token is cleared and the original 401 becomes the
same generic toast — there is no redirect to login from here. A 5xx or a non-JSON gateway body
becomes a generic toast as well. 403 is not reachable on this route: it is covered only by the
catch-all authenticated rule, with no role gate, and the request record carries no Bean Validation
constraints, so the framework cannot produce a 400 of its own either.

### 7. If the initial GET /users/me request fails (network timeout, 500 error, 401, etc.), what does the user see — an error state, a loading spinner forever, stale data, or something else?

An honest error state. The catch sets an error message and the finally always clears the loading
flag, so the card renders one line of error text plus a Retry button; the saved-phone state stays
null, so no stale or fabricated number is shown, and there is no spinner that hangs. The weakness is
that every failure collapses to the same sentence: an expired session (401 after a failed refresh)
reads identically to a 500, and nothing routes the user to re-login.
`src/pages/brand-settings.tsx:265` "Could not load your mobile number."

### 8. Are there any other API endpoints or screens in the product that fetch or modify the same underlying user profile data that /users/me operates on, and if so, do those screens reflect changes made via PATCH /users/me?

Yes for the phone column, no for the rest. The same users.phone_number column is also written by
brand registration, by the creator self-profile PATCH, and by creator onboarding — all funnelled
through the shared phone service — and it is read back by the creator self-profile response and by
two admin creator views. None of those are brand-facing screens, so for a BRAND account nothing else
in the product displays this number: this settings card is the only surface that reflects the write.
The Phone input in the Workspace Information card on the very same page is a different column on a
different endpoint and deliberately does not change when this PATCH runs, which is correct but
visually confusing — two phone fields on one settings page. For the other five fields, the profile
service is the only writer in the whole backend, so nothing can diverge; note though that the name
shown in the brand app shell comes from the login session store, not from this endpoint, so a
displayName written here would not appear in the header until the next login.

`src/components/brand/brand-layout.tsx:168` "user?.displayName"

### 9. What user-facing scenario would visibly break if GET /users/me returned stale data or PATCH /users/me silently failed to persist changes?

A brand that mistyped its mobile number at signup corrects it here, sees the card update and the
success toast, and believes it is fixed — while the row still holds the old number. This is a real
fragility, not a hypothetical: the card is repainted from the PATCH response body rather than from a
re-read, so a server that echoed the new value without committing it would look exactly like
success, and only a page reload would reveal it. The blast radius beyond this card is small because
no other brand-facing screen reads the number, but the uniqueness pre-check runs against what is
actually stored, so an apparently-saved number would still be free for another account to register.
`src/pages/brand-settings.tsx:307` "setSavedPhone(updated.phone)"

### 10. Are the /users/me routes the only way the frontend reads or writes this user data, or is there a parallel set of endpoints (like GET /users/{id}, PATCH /users/{id}) that could be serving the same function?

There is no /users/{id} at all — the controller maps the /users prefix and declares only the two
self-scoped methods, both resolving the caller from the authentication principal. For the frontend,
these two are the only read/write path to the brand's own user row. But there is a parallel path for
the same phone column on the creator side: the creator self-profile PATCH writes it with opposite
blank-means-clear semantics, and this endpoint deliberately ignores a phone sent by a non-BRAND
caller, silently, with no error. There is also a name collision worth flagging: the workspaces
getMe/updateMe pair in the same API file targets a different table entirely.
