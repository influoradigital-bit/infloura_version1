# F-0447 answers — Creator Pending-Signature Contracts List

Read from the working tree as it stands on 2026-09-04. The section exists and its four
regression tests pass; the findings below are what an honest reading turns up anyway.

### 1. Where exactly does a creator see the pending-signature contracts list — is it on the main dashboard, a dedicated contracts page, inside each deal detail view, or somewhere else entirely?

On the main creator dashboard only. It is a Card section rendered unconditionally between the
three summary tiles and the public-page card, headed by directive copy. There is no dedicated
creator contracts page and no creator nav entry for contracts; the per-deal contract tab inside
the deal room is a separate surface that shows one contract at a time, not this list. The section
renders in mock mode too, where the API layer returns an empty array by design, so a demo creator
always sees the empty state rather than the section being hidden.

`src/pages/creator-dashboard.tsx:531` "<FadeUp y={0} delay={0.02}>"

### 2. What happens when a creator has zero pending-signature contracts — does the UI show an empty state with messaging, display nothing, show a placeholder, or does the entire section disappear?

The section stays, and the card body renders a real empty state: a bordered muted panel with a
success check icon and a single sentence. The heading and description above it remain visible, so
a creator with nothing to sign still sees the section header. Nothing disappears and no placeholder
skeleton lingers.
`src/pages/creator-dashboard.tsx:555` "No contracts waiting on your signature."

### 3. If the fetch to load pending-signature contracts fails (network timeout, 500 error, 403), what does the creator see — an error message, a crash, a silent failure with no list, or does stale data remain on screen?

A destructive Alert with its own title, distinct from the empty state — this is the one thing the
new tests pin hardest. The catch block clears the list first, so no stale rows survive a failed
refetch, then sets the error string. On an ApiError the server message is surfaced verbatim; on
anything else a generic fallback sentence is used. Note the consequence of surfacing the raw server
message: a 403 from a non-creator principal would render the backend WRONG_USER_TYPE text directly
to the user, which is accurate but not written as user-facing copy.

### 4. What does the UI show while pending-signature contracts are loading — a skeleton loader, a spinner, nothing at all, or does previously loaded data stay visible?

Two stacked skeleton bars inside the card, marked aria-hidden so screen readers are not told about
placeholder furniture. The loading flag starts true, so the skeletons are what a creator sees on
first paint. There is no separate refetch path, so the question of previously loaded data staying
visible during a reload never arises — the effect runs once per mount and the skeleton branch is
only ever the first-load branch.

### 5. If a creator clicks on an item in the pending-signature contracts list, where does it navigate — to the full contract PDF, a signature flow, the parent deal detail page, or does the click do nothing?

Each row is a whole-row react-router Link to the creator chat deal room, keyed to the contract
collaborationId, with a query param that opens the contract tools panel. It is deliberately
discovery-only: no PDF, no inline signing. The chat page reads both params and the tab value
contract is one of its three valid panels, so the panel does open. One fragility worth naming: the
link is built from collaborationId while the deal room decides whether to render the contract panel
from the deal row contractId returned by a different endpoint, so the two can disagree.

### 6. What happens if another party (brand or admin) signs a contract while the creator's pending list is displayed on screen — does the list auto-refresh to remove it, update only on manual page refresh, or remain stale showing a contract that is no longer pending?

It stays stale. The effect that loads the list has an empty dependency array and there is no
polling, no websocket, no focus or visibility listener, and no manual refresh control anywhere in
the section. The list is fetched once on mount and never again. It updates only when the component
remounts — a full browser reload, or navigating away to another creator route and back. As long as
the creator sits on the dashboard, a contract signed elsewhere keeps showing.

### 7. What information does each pending-signature contract item actually display — deal title, brand name, contract value, creation date, signature deadline, just a Sign Now button, or some other combination?

Only three things: a signature icon, the formatted total amount, and a subtitle giving the
milestone count plus a fixed phrase. No deal title, no campaign name, no brand name, no creation
date, no signature deadline, no contract status, no Sign Now button. This is a real gap for
identification: a creator with two contracts of the same value sees two visually identical rows and
cannot tell which brand either belongs to without clicking through. The fields to do better are
already on the record the API returns — effectiveDate, expirationDate and createdAt are all on the
typed shape and are simply not rendered.
`src/pages/creator-dashboard.tsx:570` "{formatINR(contract.totalAmount)}"
`src/pages/creator-dashboard.tsx:574` "brand signed, your turn"

The fixed phrase is also not always true. The card description promises the brand has signed, and
the row subtitle asserts it, but the backing query filters on the creator signature being null and
nothing else. A DRAFT contract the brand has not signed, or a CANCELLED one, is returned by that
query and rendered under copy claiming the brand already signed and it is the creator turn. The
frontend never reads brandSignedAt or status to check.

### 8. Is there a separate comprehensive Contracts page (not just the pending list) where creators can see all contracts (pending, signed, rejected, expired) — and if so, does the pending-signature data appear there identically, differently, or not at all?

No. There is no creator contracts page and no creator contracts route; the creator sidebar goes
Home, Deals, Campaigns, Applications, Co-pilot, Analytics, Wallet, then a Manage group with no
contracts entry. A creator can only reach a signed or cancelled contract by opening the specific
deal room and its contract panel. The backend is not the blocker — the list endpoint already
serves every contract for a creator, optionally filtered by deal, and the frontend client wraps it,
but nothing on the creator side renders it.

### 9. What happens if a pending-signature contract has missing or null data (no associated deal name, null brand, missing creation timestamp) — does it render with fallback placeholders, crash the list, skip that entry silently, or show raw null/undefined?

Deal name, brand and creation timestamp are not rendered at all, so their absence is invisible by
construction. A null or missing total amount degrades safely because the currency formatter returns
an em dash for null and NaN rather than a fabricated zero. The one unguarded field is milestones:
the row dereferences its length with no fallback, so a null or absent milestones array would throw
during render and take down the whole dashboard, not just the row. In practice the backend always
maps a list there, so this is latent rather than reachable today. A null collaborationId would not
crash but would silently produce a dead link with the literal string null in the query.

### 10. Can a creator actually complete the signature flow end-to-end from this list — does clicking through lead to a functional signature capture mechanism (typed name, drawn signature, upload), does submitting the signature succeed, and does the contract then disappear from the pending list immediately or require a refresh?

Mostly yes, with two caveats. The row opens the deal room contract panel, which renders a typed
full-name input and a Sign button, disabled until the trimmed name is non-empty; there is no drawn
signature or upload path, typed name is the whole mechanism. Submitting posts to the creator sign
endpoint with that name and, on success, updates the local status and toasts. Caveat one: the panel
only renders when the deal row carries a contractId, otherwise the creator lands on an honest but
dead-ending no-contract-yet state, so a row from the unsigned list can navigate to a screen with no
Sign control. Caveat two: the contract does not disappear immediately. Signing happens on the chat
page and nothing notifies the dashboard; the dashboard list only re-fetches when the page remounts,
so returning via a client-side link or a reload clears it, while the dashboard tab left open behind
it keeps showing the signed contract.
