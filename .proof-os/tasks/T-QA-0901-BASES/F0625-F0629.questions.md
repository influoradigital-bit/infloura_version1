# QA Questions: F-0625 & F-0629 (Contract Signature Dashboard + Deal Room Links)

1. What happens when the "Contracts awaiting your signature" section renders a contract that has zero milestones in the backend response?

2. What happens when a contract in the dashboard list has a `null` or `undefined` value for a required field (e.g., `brandName`, `campaignTitle`, `contractId`) — does the UI crash, render blank, or show a fallback?

3. When a creator clicks a contract row in the dashboard, and the `contractId` in the URL is valid but belongs to a *different* creator, does the deal room show that other creator's contract data, return a 403, or fail in another way?

4. When a creator follows a dashboard link to `/creator-chat?dealId=X` but that deal or contract no longer exists (deleted, or the creator was removed from it), what does the UI display?

5. When a dashboard contract link is followed with a *malformed* or *non-numeric* `dealId` or `contractId` parameter, does the deal room page crash, show an error boundary, or gracefully handle the invalid input?

6. If the API returns a contract with milestones but one milestone object is missing a required field (e.g., `amount`, `description`, `deadline`), does the contract detail view in the deal room render correctly, partially, or throw an error?

7. When a creator refreshes the deal room page (`/creator-chat?dealId=X`) directly (not via dashboard navigation), does it correctly fetch and display the contract, or does it rely on in-memory state that is now missing?

8. Is there a falsified test that *starts* with a contract having no milestones in the mock API response, renders the dashboard, and asserts the UI does not crash and shows a specific fallback message?

9. Is there a falsified test that *starts* with an invalid `dealId` (e.g., `dealId=99999` or `dealId=abc`), navigates to `/creator-chat?dealId=99999`, and asserts the page shows an error state (not a crash, not someone else's data)?

10. When the dashboard link transitions to the deal room, is the `dealId` or `contractId` parameter validated against the logged-in creator's identity on the backend before returning contract data, or does the frontend assume the API will never return unauthorized data?
