## What was observed

The gate runs and exits 1 on the real repo (78 *Controller.java, 438 FE .ts/.tsx, 158 endpoints matched, 21 call sites compared, 2 instances), and both reported instances are genuine — I traced creatorSearchQuery (src/lib/api.ts:1567) emitting 10 keys against CreatorController.search binding 16, and the 6 names it prints (categories, isVerified, languages, maxEngagementRate, minEngagementRate, sortBy) match F-0431 exactly; the second, GET /creator/applications accepting `status` that its only caller (src/pages/creator-applications.tsx:47) never sends while filtering client-side over a 50-row server page, is a real dead capability. Vacuous-pass handling is genuinely good and is the gate's strongest property: an empty tree, hollow directories, and a tree of irrelevant Java/TS all exit 2, never 0, and it carries matched==0 / compared==0 guards on top. It also leaves no litter — the source contains no open/write_text/mkdir/subprocess, and the only .pyc appeared when I imported it for instrumentation into a pre-existing, gitignored __pycache__ (the .proof-os/rc churn I saw is a different gate run by a concurrent session). It is nonetheless refuted, on green-on-bad-input. Because the vacuity guards mask results in a one-endpoint fixture, I built an isolated mirror with a clean ballast endpoint so matched>0 and compared>0 — the realistic condition in this repo — and 11 of 12 constructed drift instances exited 0: arrow-function helper, double-quoted verb/path, verb hoisted to a const, path hoisted to a const, const-object method helper, handler in *Resource.java, `params:` instead of `query:`, a call site in a *.test.ts-named file, a URLSearchParams builder, a cross-module helper, and a client sending zero params. Only the plain object literal — the exact shape of the records the gate was written from — was caught. The decisive demonstration is on the real repository: rewriting `function creatorSearchQuery(params...)` to `const creatorSearchQuery = (params...) =>`, a purely cosmetic refactor that does not touch the defect at all, dropped the output from 2 instances to 1 and made F-0431 — the gate's own headline record — vanish while the defect remained fully present (compared fell 21→20, and nothing exited 2 to signal the loss). A gate whose named record disappears under a no-op edit is not proven. I also found the detector red-on-good-input in 3 of 7 legitimate synthetic patterns, all in the IGNORED INPUT direction: non-query assignments inside a resolved helper body (`opts.signal = ...` reported as params signal, retries), a nested object literal used as a query value (reported as deep, nested), and one helper shared by two endpoints (superset key zulu). None fire on the repo today only because it currently has zero IGNORED-INPUT matches, so today's false-positive count is 0, but they would fire on the first such addition. I restored everything: api.ts is byte-identical to its pre-test backup (sha256 98874e2b…) and no probe files remain.

## Required fix (the minimum change that would make this gate real)

Two changes, in priority order. (1) Stop keying detection on one hand-written call syntax. The FE side must resolve helpers regardless of declaration form — `const f = (p) => {...}`, `const f = function(){}`, and object-method builders — not just `function f(`; FN_DEF_RE_T at line 307 recognizes only the `function` keyword. Likewise CALL_RE (line 304) must accept double-quoted verbs/paths and verb/path values reached through a const, and _query_value must accept the `params:` option key as well as `query:`. Each of these is a one-line regex today and each one silently zeroes the finding. (2) Assert coverage, not just non-zero counts. The gate matched 158 endpoints but compared only 21 call sites (167 detected FE sites, 145 skipped for having no query keys); the existing `compared == 0` guard is far too weak to notice that a refactor dropped a site from the compared set. It needs a committed floor — a checked-in expected-coverage number, or a per-record assertion that the F-0408/F-0431 call sites at src/lib/api.ts:1670 and the CreatorController.search handler are still present in the compared set — so that losing an instance to a parsing miss exits 2 (UNAVAILABLE) instead of 0 (clean). Secondary: scope _keys_from to the returned query object rather than the whole resolved helper body, and exclude nested object-literal values, to remove the IGNORED-INPUT false positives demonstrated below.
