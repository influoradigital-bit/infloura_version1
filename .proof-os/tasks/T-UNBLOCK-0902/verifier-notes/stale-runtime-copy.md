## What was observed

Ran on the real repo: exit 1, 4 findings (_oracles.py, build.sh, eslint.sage.json, eslint.sage.mjs), canonical auto-resolved to .proof-os/.runtime/os042 (0.4.2, 26 manifest records), 16 candidates compared. All 4 are real byte-divergences, confirmed by diff — 0 false positives; eslint.sage.json (591B vs 1417B, missing root/parserOptions/ecmaFeatures.jsx) and eslint.sage.mjs (1707B vs 5083B, missing the shared CORE_RULES block) are unambiguously stale-behind copies, while build.sh and _oracles.py are local forks (project _oracles.py is canonical plus a 7-line F-0333 patch) that the gate flags by explicit stated design. Detector logic is strong: in a sandboxed copy I proved exit 0 on a clean tree and exit 1 on the identical directory after mutating content, and it caught every evasion I tried — a single appended newline, a whole-file CRLF conversion, a comment-only insertion, gutting frontmatter.py to `sys.exit(0)`, deleting shared _rc.py (MISSING SHARED), and planting a gutted confirm.py where no project copy existed (scanned 16→17, exit 1). No vacuous pass: empty dir exit 2, repo src/ exit 2, nonexistent dir exit 2, manifest-less canonical exit 2, PROOF_OS_HASHER=md5sum exit 2, unknown arg exit 2. It creates and modifies nothing — a full find snapshot of .proof-os before and after was byte-identical, and it writes no rc record. It is REFUTED on baseline selection. Candidate trees are ranked purely by the version string in the manifest header, with no floor on how much that manifest covers, and the vacuous guard only requires COMPARED>=1. I built a directory containing gates/citations.py (an already-matching file) plus a two-line MANIFEST.sha256 whose header read "proof-os 0.9.9", dropped it at .proof-os/.runtime/os999/, and ran the gate with NO flags and NO environment variables: it selected os999 over the real 0.4.2 tree, reported "scanned: 1 candidate file(s) compared", "count: 0 finding(s)", "VERDICT: aligned (proved)", exit 0 — on the exact same tree that still contained all 4 unrepaired drifts, none of which was touched. Same green reproduced via --canonical and via PROOF_OS_CANONICAL. .proof-os/.runtime/ already holds two such trees (os042 and a 0.4.1 proof-os), so a partial or interrupted unpack reaches this state by accident, not only by attack, and the gate prints an unqualified "proved" while having examined 1 of 16 comparable files. Two further misses, both disclosed in its own NOT CHECKED line: a stale stub at gates/legacy/citations.py and a renamed stub citations_v2.py both left it exit 0. The gate is sound at what it compares; it is unproven at choosing what to compare against, so it must not be recorded as proven.

## Required fix (the minimum change that would make this gate real)

Add a baseline-coverage floor to the canonical-tree selection so a thin manifest cannot win. Concretely: (a) after picking BEST_KEY, keep every discovered candidate and compute, for each, how many project files in $PROJECT_GATES share a name with its manifest's gates/ entries; refuse (exit 2) if the winner's shared-name count is lower than any other discovered candidate's, i.e. never let a higher version string buy a smaller baseline; (b) replace the `COMPARED -eq 0` vacuous guard with a coverage guard — count the project gate files that any discovered canonical tree names, and if COMPARED is less than that number, exit 2 with "baseline covers N of M project gates" rather than printing "aligned (proved)"; (c) do not accept a candidate whose MANIFEST.sha256 names fewer gates/ files than some floor (e.g. < 5) without saying so on the VERDICT line. Independently, tie the manifest's version header to something the project cannot mint locally (the plugin's own signed/pinned version) so an unpacked directory under .proof-os/.runtime/ cannot declare itself newest.
