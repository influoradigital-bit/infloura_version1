# TrendPullJob design (cached from workflow Investigate)

## Summary
The n8n workflow (trendspark/n8n/trend-pull-workflow.json, 451 lines) is a 4-source fan-out (TMDb upcoming IN, NewsAPI top-headlines IN/entertainment, YouTube videos.list mostPopular IN, and a Google-Trends node that is a deliberate STUB returning []), an append-merge, a normalizer that shapes each payload into {text, source, category}, an inline "Theme Tagger + row builder" Code node, a MySQL INSERT of exactly 12 columns into `trends`, and a SEPARATE 06:30 IST trigger running `DELETE FROM trends WHERE expires_at < UTC_TIMESTAMP(6)`. Critically, the Java side ALREADY owns half the tagger: ThemeMatchService (influora-api/src/main/java/com/influora/service/trendspark/ThemeMatchService.java) loads trendspark/theme-taxonomy.json at @PostConstruct and its themesForText(String) is byte-for-byte the JS KEYWORD_TO_THEMES containment match plus the closed-vocab filter — I verified the two vocabularies are identical (40 themes, 57 keyword mappings, no diff) by running `node trendspark/n8n/tagger-sync.check.js` (ALL PASS, 11 checks) and diffing the module against the JSON in node. So the keyword tagger must NOT be re-ported; it must be called. What is NOT in Java is deriveCampaignType — nothing loads influora-api/src/main/resources/trendspark/campaign-rulebook.json, which is on the classpath but has zero Java readers. Outbound HTTP: this repo has two established idioms and both are needed — Spring `RestClient`, lazily built inside a synchronized block, absolute URI hand-built (MetaGraphApiClient.java L48-77 and buildUri at L154-200, whose javadoc documents why UriBuilder.path() must not be used) for third-party GETs, and plain `java.net.http.HttpClient` pinned to HTTP/1.1, never-throws, returns null on any failure (TrendSparkAiClient.java) for the internal influora-ai leg. Job conventions from CreatorThemeTaggingJob/CreatorCaptionSyncJob: @Scheduled(cron = "${...}", zone = "UTC") + @SchedulerLock, flag check as the literal first statement with an info log and a bare return, per-item try/catch, and one summary log line of counters at the end. THE BLOCKER: the expiry DELETE cannot be ported as written. V20260721140000__creator_nudge_log.sql:33 adds `CONSTRAINT fk_creator_nudge_log_trend FOREIGN KEY (trend_id) REFERENCES trends (id)` with no ON DELETE clause, so InnoDB defaults to RESTRICT; that migration postdates the workflow. The moment the Co-pilot logs one suggestion, the single bulk DELETE fails with MySQL 1451 and rolls back entirely, so nothing ever expires. ON DELETE CASCADE is not the fix — creator_nudge_log's generated-column unique key is the per-creator/day cap backstop, and cascading would let a creator be re-nudged. Recommendation is soft expiry (TrendRepository.findActive already filters expiresAt > :now and both readers go through it).
